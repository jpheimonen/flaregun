# 016: Orchestrator: up and down commands

## Context

The orchestrator is the command handler for `flaregun up` and `flaregun down` — the two runtime commands that start and stop the entire system. `flaregun up` is the primary way users run flaregun: it syncs Cloudflare state, starts the admin UI, starts local services, runs the tunnel, and blocks until shutdown. `flaregun down` performs a graceful shutdown.

The personal-homepage project has a simpler version in `up.ts`: it checks prerequisites, syncs, launches services (without restart logic), starts the tunnel, and registers SIGINT/SIGTERM handlers. Flaregun's orchestrator expands this significantly: it integrates the process supervisor (step 011) instead of bare subprocess management, starts the admin backend (step 012), uses the environment manager (step 003) for credential validation, and has a proper shutdown sequence with ordering guarantees.

The orchestrator ties together nearly every component from previous steps into a cohesive runtime. It is the "main function" of flaregun's runtime mode.

## Deliverables

### Up command handler

The command handler invoked when the user runs `flaregun up`.

**Startup sequence (executed in order):**

1. **Load and validate config:** Read `flaregun.yml` via the config loader (step 002). If the config is invalid, report the validation errors and exit immediately. No other operations are performed.

2. **Load environment:** Load the `.env` file and validate that all required environment variables are present via the environment manager (step 003). For the `up` command, all variables are required (API token, account ID, zone ID, and tunnel token). If any are missing, report which variables are missing, suggest `flaregun setup`, and exit.

3. **Load lock file:** Load `flaregun.lock` via the lock file manager (step 003). If the file doesn't exist, initialize an empty lock file state (first run).

4. **Check prerequisites:** Verify that `cloudflared` is installed and available on PATH via `binaryExists()`. If not found, report a descriptive error with installation instructions and exit.

5. **Initialize SDK client:** Create the Cloudflare SDK client from the loaded credentials via the client wrapper (step 003).

6. **Run full sync:** Execute the full sync orchestrator (step 005) — Access applications, Access policies, tunnel ingress, DNS records, redirect rules. The sync uses the SDK client, parsed config, credentials, and lock file state. The lock file is saved after each step that mutates state. If sync fails, report the error and exit. The system should not start services if sync failed, as Cloudflare state may be inconsistent. Note: at this point the admin backend port is not yet known, so the tunnel ingress sync runs without the admin ingress rule. The admin rule is added in step 9 below.

7. **Start admin UI backend:** Create and start the admin backend (step 012), injecting the process supervisor, hot-reload engine, config file path, and pre-built SPA directory. The backend selects an available port and reports it. The orchestrator stores this port for the ingress rule.

8. **Start local services:** For each local service in the config, call the process supervisor's (step 011) start method. The supervisor spawns the process and begins monitoring. Services that fail to start on the first attempt enter the supervisor's normal crash → backoff → retry cycle.

9. **Update tunnel ingress with admin port:** Now that the admin backend's port is known, re-run the tunnel ingress sync (step 005, ingress function only) with the admin port included. This ensures the `admin.domain` ingress rule points to the correct port.

10. **Start cloudflared tunnel:** Spawn the `cloudflared tunnel run` command with the tunnel token from the environment. The tunnel process runs for the lifetime of `flaregun up`.

11. **Print startup summary:** Display a summary listing all services with their initial states, the admin UI URL (`https://admin.domain`), and tunnel status.

12. **Block:** Block on the tunnel process. The orchestrator remains running until the tunnel exits or a shutdown signal is received.

### PID file management

The `flaregun up` process writes a PID file so that `flaregun down` can find and signal it.

**Behavior:**

- **Write on startup:** After all subsystems have started (but before blocking on the tunnel), write the current process PID to `.flaregun.pid` in the same directory as `flaregun.yml`.
- **Read on down:** The `down` command reads the PID from `.flaregun.pid` to find the running process.
- **Cleanup on exit:** The PID file is deleted during the shutdown sequence (after all subsystems have stopped, before the process exits). This ensures a clean state after normal shutdown.
- **Stale PID handling:** If `.flaregun.pid` exists but the process with that PID is not running (stale file from a crashed or force-killed instance), `flaregun down` should detect this, report that no running instance was found, and delete the stale PID file.
- **Atomic write:** Write the PID file atomically (write to a temp file, then rename) to avoid race conditions where `down` reads a partially written file.

### Down command handler

The command handler invoked when the user runs `flaregun down`.

**Behavior:**

- The `down` command performs a graceful shutdown of the running system. It does not modify Cloudflare state — DNS records, Access applications, the fallback Worker, and Pages deployments all remain in place so the down page handles unavailable services.
- Read the PID from `.flaregun.pid` in the current directory (or the directory containing `flaregun.yml`).
- If the PID file does not exist, report that no running instance was found and exit.
- If the PID file exists, check whether the process with that PID is still running.
- If the process is running, send it a SIGTERM signal. This triggers the `up` process's signal handler, which executes the shutdown sequence.
- If the process is not running (stale PID file), report that no running instance was found, delete the stale PID file, and exit.
- After sending the signal, `flaregun down` exits immediately — it does not wait for the `up` process to finish shutting down. The `up` process handles its own shutdown sequence and cleanup.

### Shutdown sequence

The ordered shutdown sequence triggered by SIGINT, SIGTERM, or `flaregun down`.

**Behavior (executed in order):**

1. **Stop the cloudflared tunnel:** Kill the tunnel process. Once the tunnel is down, the domain's subdomains become unreachable from the internet. The fallback Worker's proxy-with-fallback detects the unreachable origin and redirects to the down page.

2. **Stop all local services:** Call the process supervisor's shutdown method (step 011). The supervisor sends SIGTERM to all child processes, waits for the graceful timeout, and force-kills stragglers. After shutdown, all services are in the `stopped` state.

3. **Stop the admin UI backend:** Call the admin backend's stop method (step 012). This closes the HTTP server and any open WebSocket connections.

4. **Exit:** Exit the process with code 0.

**Ordering rationale:** The tunnel is stopped first so that incoming requests start hitting the down page immediately, while services are still running and can finish processing any in-flight work. Services are stopped second. The admin backend is stopped last since it's only accessible through the tunnel (which is already down).

### Signal handling

The orchestrator installs signal handlers for graceful and forced shutdown.

**Behavior:**

- **First SIGINT or SIGTERM:** Trigger the shutdown sequence described above. Log "Shutting down..." to indicate the shutdown is in progress.
- **Second signal (during shutdown):** Force-exit immediately with `process.exit(1)`. This is the escape hatch if the graceful shutdown gets stuck (e.g., a child process ignores SIGTERM and the timeout hasn't elapsed yet). Log "Force exiting..." before the exit.
- Signal handlers are registered after all subsystems are started but before blocking on the tunnel process.

### Tunnel process management

The orchestrator spawns and monitors the cloudflared tunnel daemon.

**Behavior:**

- Spawn `cloudflared tunnel run --token <token>` as a child process. Capture or inherit stdout/stderr (the tunnel daemon produces connection status output that is useful for debugging).
- Monitor the tunnel process's exit event. If the tunnel exits unexpectedly (not triggered by shutdown):
  - Log a warning indicating the tunnel has disconnected
  - All local services continue running — they are still accessible locally, just not from the internet
  - The fallback Worker handles the unreachable origin by redirecting to the down page
  - Optionally attempt to restart the tunnel after a short delay (single retry). If the restart also fails, log the error and continue running without the tunnel.

### Dependency injection for testability

The orchestrator accepts all subsystem dependencies as injectable parameters, following the `UpDeps` pattern from the personal-homepage project.

**Injected dependencies:**

- Sync function (or full sync orchestrator)
- Process supervisor instance
- Admin backend factory (or instance)
- Tunnel spawner function
- Config loader function
- Environment manager
- Lock file manager
- SDK client factory

**Default implementations** use the real subsystems. Tests provide mock implementations that track call order and arguments.

### Tests

Tests use the dependency injection pattern to mock all subsystems and verify orchestration logic without real processes, servers, or API calls.

**Startup sequence tests:**
- The orchestrator validates config, environment, lock file, prerequisites, and sync in the correct order
- A config validation failure aborts startup before any other operations
- A missing environment variable aborts startup with a descriptive error suggesting `flaregun setup`
- A missing `cloudflared` binary aborts startup with installation instructions
- A sync failure aborts startup before services are started
- The admin backend is started before local services
- Local services are started via the process supervisor after the admin backend
- The tunnel ingress is updated with the admin backend's port before starting the tunnel
- The tunnel is started after all services and the admin backend
- A startup summary is printed after all subsystems are running

**Shutdown sequence tests:**
- The shutdown sequence stops the tunnel first, then services, then the admin backend
- After shutdown, the process exits with code 0
- A SIGINT triggers the shutdown sequence
- A SIGTERM triggers the shutdown sequence
- A second signal during shutdown triggers a force exit

**PID file tests:**
- The `up` command writes a PID file after all subsystems start
- The PID file contains the current process PID
- The PID file is deleted during the shutdown sequence
- A stale PID file (process not running) is detected and cleaned up

**Down command tests:**
- The down command reads the PID file and sends SIGTERM to the running process
- The down command reports if no PID file exists (no running instance)
- The down command detects a stale PID file, reports no running instance, and deletes the stale file

**Tunnel management tests:**
- An unexpected tunnel exit logs a warning but does not stop services
- The system continues running after tunnel disconnection

**Dependency injection tests:**
- All subsystems are called with the correct arguments (verified via mock call tracking)
- Call order matches the specified startup sequence
