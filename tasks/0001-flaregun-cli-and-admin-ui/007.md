# 007: Functions scaffolder and wrangler config generator

## Context

This step creates two utilities that the deploy pipeline (step 009) depends on: the functions scaffolder and the wrangler config generator. Both produce files that are internal artifacts — the user never writes or maintains them.

The **functions scaffolder** solves a bootstrapping problem: when a Pages service declares cloud resources (`database`, `bucket`, `kv`) but has no `functions/` directory, there's nothing to bind those resources to. The scaffolder creates a starter `functions/` directory with an example handler that demonstrates the declared bindings and a tsconfig referencing the Cloudflare Workers types. This is a one-time operation — if `functions/` already exists, the scaffolder does nothing.

The **wrangler config generator** produces temporary `wrangler.toml` files for two purposes: deploying Pages projects (with `pages_build_output_dir` and D1/R2/KV bindings) and deploying the fallback Worker (with the wildcard route pattern). These files are written to a temporary directory, used by wrangler during deployment, and cleaned up afterward. The user never sees them.

The personal-homepage project has a static `wrangler.toml` for its Worker but no generated configs and no functions scaffolding. Both utilities are entirely new for flaregun. However, the naming conventions established in step 006 (resource provisioner) are reused for Pages project names and Worker names.

## Related Code

Existing files/patterns to reference or extend:

- `../personal-homepage/worker/wrangler.toml` — The existing fallback Worker config. Contains the Worker name (`heimonen-cc-fallback`), the main entry point, a compatibility date, and a wildcard route pattern with zone name. Flaregun's wrangler config generator produces the same structure but with the domain name injected from config instead of hardcoded.

- `../personal-homepage/scripts/deploy.ts` (lines 95–138) — `deployHomepage()` demonstrates how wrangler is invoked for Pages deployment: `wrangler pages deploy <dir> --project-name <name>`. With a generated `wrangler.toml` that includes `pages_build_output_dir`, the deploy command changes to `wrangler pages deploy` run from the directory containing the generated config. This context informs how the config generator's output is consumed.

- `../personal-homepage/scripts/deploy.ts` (line 182) — The Pages project naming convention: `config.domain.replace(/\./g, "-")`. Flaregun extends this to include the service name for multi-service support.

- Step 006's resource naming convention — The provisioner already derives resource names from domain + service name. The wrangler config generator should use the same or compatible naming convention for Pages project names (since wrangler bindings reference the resource IDs from the lock file, not the names, consistency matters primarily for the project name itself).

- Step 003's lock file manager — The wrangler config generator reads resource IDs from the lock file to populate D1/R2/KV binding declarations. It does not write to the lock file.

## Reuse Opportunities

- **Naming convention from step 006** — The resource naming utility can be reused or extended for deriving Pages project names and the fallback Worker name from the domain. The same domain-to-prefix transformation (dots → hyphens) applies.

- **Config types from step 002** — The scaffolder and config generator both consume the parsed config object from the config loader. The scaffolder needs to know which cloud resources a service declares. The config generator needs the service's `dist` path, cloud resource declarations, and domain.

- **Lock file types from step 003** — The config generator reads resource IDs from the lock file state to populate bindings. It uses the same lookup interface the provisioner and sync engine use.

## Deliverables

### Functions scaffolder

A utility that creates a starter `functions/` directory for Pages services that declare cloud resources but lack a functions directory.

**Behavior:**

- Accept a service's config (including its cloud resource declarations and functions path) and the project root as parameters
- Determine the target functions directory path: use the service's `functions` config field if specified, otherwise default to `functions/` relative to the service's project directory
- **Guard: never overwrite.** If the target directory already exists, do nothing and return an indicator that scaffolding was skipped. This is a hard requirement — the scaffolder must never modify or replace an existing functions directory.
- If the target directory does not exist, create it with:
  - **An example API handler file** that demonstrates how to use the declared bindings. The content should be a valid Pages Function (a TypeScript file exporting an `onRequest` handler) that references only the bindings the service actually declared:
    - If `database: true`: the example shows usage of the `DB` binding (D1 database)
    - If `bucket: true`: the example shows usage of the `BUCKET` binding (R2 bucket)
    - If `kv: true`: the example shows usage of the `KV` binding (KV namespace)
    - If multiple resources are declared, the example shows all of them
    - If no cloud resources are declared, the scaffolder should not be invoked (this is the caller's responsibility), but if it is, it should produce a minimal handler with no binding usage
  - **A tsconfig.json** that extends or references `@cloudflare/workers-types` so the bindings have proper type definitions in the user's editor
- Return an indicator of what was created (scaffolded vs. skipped)

**Trigger context:** The scaffolder is called by the deploy pipeline (step 009) and the build command (step 010) — not directly by the user. It runs after the service's build step but before the functions-copy-into-dist step.

### Wrangler config generator — Pages projects

A utility that generates a `wrangler.toml` file for deploying a Pages project via wrangler.

**Behavior:**

- Accept the service config, the domain name, and the lock file state as parameters
- Generate a `wrangler.toml` with:
  - **Project name:** Derived from the domain and service name using a consistent naming convention (same transformation as resource naming — dots replaced with hyphens, combined with service name)
  - **`pages_build_output_dir`:** Pointing to the service's `dist` directory path
  - **D1 binding** (if `database: true`): A `[[d1_databases]]` section with binding name `DB`, the database name from the naming convention, and the database ID from the lock file
  - **R2 binding** (if `bucket: true`): A `[[r2_buckets]]` section with binding name `BUCKET` and the bucket name from the lock file
  - **KV binding** (if `kv: true`): A `[[kv_namespaces]]` section with binding name `KV` and the namespace ID from the lock file
  - If the service has no cloud resources, no binding sections are included
- Write the generated file to a temporary directory (not in the user's project tree)
- Return the path to the generated file so the deploy pipeline can point wrangler at it

**Missing lock file entries:** If a service declares a cloud resource but no corresponding ID exists in the lock file, the generator should throw a descriptive error. This indicates the resource provisioner (step 006) was not run before the config generator — a programming error in the deploy pipeline sequencing.

### Wrangler config generator — Fallback Worker

A utility that generates a `wrangler.toml` file for deploying the fallback Worker.

**Behavior:**

- Accept the domain name as a parameter
- Generate a `wrangler.toml` with:
  - **Worker name:** Derived from the domain (e.g., `example-com-fallback` for `example.com`)
  - **Main entry point:** Pointing to the generated Worker source file (the fallback Worker generator in step 008 produces this file in the same temporary directory)
  - **Compatibility date:** A recent, fixed date
  - **Route:** A wildcard route pattern matching all subdomains of the domain, with the zone name set to the domain
- Write the generated file to a temporary directory (same directory where the fallback Worker source will be written by step 008)
- Return the path to the generated file

### Temporary directory management

Both generators write files to temporary directories that are cleaned up after deployment. The step should provide a utility for creating and managing these temporary directories.

**Behavior:**

- Create a temporary directory in a standard location (OS temp directory or a `.flaregun/tmp` subdirectory)
- Return the path for the caller to use
- Provide a cleanup function that removes the directory and all its contents
- The deploy pipeline (step 009) is responsible for calling cleanup after wrangler completes — this step just provides the mechanism

### Tests

**Functions scaffolder tests:**

- When the functions source directory does not exist and the service declares `database: true`, a functions directory is created containing an example handler that references the `DB` binding
- When the functions source directory does not exist and the service declares `bucket: true`, the example handler references the `BUCKET` binding
- When the functions source directory does not exist and the service declares `kv: true`, the example handler references the `KV` binding
- When the service declares multiple cloud resources, the scaffolded example references all declared bindings
- A tsconfig.json referencing `@cloudflare/workers-types` is created in the scaffolded directory
- When the functions source directory already exists, no scaffolding occurs and no files are written (never overwrites)
- Scaffolding creates the directory at the path specified by the service's `functions` config field
- Scaffolding creates the directory at the default `functions/` path relative to the service when no `functions` field is specified
- The scaffolded handler file is valid TypeScript that would compile with the Cloudflare Workers types (structural validity, not a full compile check)

**Pages wrangler config tests:**

- Generated Pages wrangler.toml contains the correct `pages_build_output_dir` pointing to the service's dist directory
- The project name follows the naming convention derived from domain and service name
- A service with `database: true` produces a wrangler.toml with a `d1_databases` section containing binding name `DB` and the database ID from the lock file
- A service with `bucket: true` produces a wrangler.toml with an `r2_buckets` section containing binding name `BUCKET` and the bucket name from the lock file
- A service with `kv: true` produces a wrangler.toml with a `kv_namespaces` section containing binding name `KV` and the namespace ID from the lock file
- A service with all three cloud resources produces a wrangler.toml with all three binding sections
- A service with no cloud resources produces a wrangler.toml with no binding sections
- If a service declares a cloud resource but the lock file has no corresponding entry, the generator throws a descriptive error
- The generated file is written to a temporary directory, not in the user's project tree

**Fallback Worker wrangler config tests:**

- Generated fallback Worker wrangler.toml contains the correct Worker name derived from the domain
- The Worker name uses the same domain-to-hyphen transformation as other naming conventions
- The wildcard route pattern matches all subdomains of the domain
- The zone name matches the domain from config
- The main entry point field is present and points to the expected Worker source filename
- A compatibility date is set
- The generated file is written to a temporary directory

**Temporary directory tests:**

- Creating a temp directory returns a valid path to an existing directory
- The cleanup function removes the directory and all its contents
- Cleaning up a directory that has already been removed does not throw
