# 006: Resource provisioner

## Context

The resource provisioner handles creating and destroying Cloudflare cloud resources — D1 databases, R2 buckets, and KV namespaces — via the Cloudflare SDK. This is entirely new functionality: the personal-homepage project has no D1, R2, or KV usage at all. However, the provisioner follows the same patterns established by the sync engine: dependency-injected SDK client, lock-file-based idempotency, and the mock client test pattern from steps 004/005.

The provisioner is separate from the sync engine because it operates at a different time. Sync runs during `flaregun up` to configure access control, tunnel routing, DNS, and redirect rules. Provisioning runs during `flaregun deploy` to ensure cloud resources exist before wrangler deploys a Pages project that binds to them. The provisioner is also invoked by `flaregun destroy` to tear down all resources.

Resource creation is idempotent via the lock file: before creating a resource, the provisioner checks the lock file for an existing ID. If found, it skips creation. The lock file is the sole source of truth — even if a resource with the same name exists in Cloudflare but is not tracked in the lock file, the provisioner creates a new one. This design keeps the logic simple and avoids fragile name-matching heuristics against remote state.

Resource naming follows a domain+service convention so that resources are recognizable in the Cloudflare dashboard (e.g., `example-com-blog-db` for a D1 database belonging to the `blog` service on `example.com`).

## Deliverables

### Resource naming (reuse from step 005)

The resource naming convention utility was introduced in step 005 as a shared module. The provisioner imports and uses it to derive D1 database names, R2 bucket names, and KV namespace names. The provisioner appends resource-type suffixes (e.g., `-db`, `-bucket`, `-kv`) to the base name produced by the shared utility. No new naming logic is needed in this step — it reuses the existing utility.

### Provisioning function

A function that provisions all declared cloud resources for a set of Pages services.

**Behavior:**

- Accept the Cloudflare SDK client, the parsed config, the account ID, and the lock file state as parameters
- For each Pages service in the config that declares cloud resources:
  - **D1 database (`database: true`):** Look up the lock file for an existing D1 database ID for this service. If found, skip. If not found, create a new D1 database via the SDK using the naming convention. Store the returned database ID in the lock file.
  - **R2 bucket (`bucket: true`):** Same pattern — look up lock file, skip if found, create via SDK if not, store the bucket name in the lock file.
  - **KV namespace (`kv: true`):** Same pattern — look up lock file, skip if found, create via SDK if not, store the namespace ID in the lock file.
- Local services are skipped entirely (cloud resources are only valid on Pages services — this was enforced at config validation in step 002)
- Services with no cloud resource declarations are skipped
- Save the lock file after all provisioning is complete
- Return a summary of what was provisioned (created vs. skipped, per service and resource type)

**Idempotency:** The lock file is the sole source of truth. If the lock file says a resource exists (has an ID), the provisioner trusts it and does not verify against Cloudflare. If the lock file has no entry, the provisioner creates a new resource regardless of whether a resource with the same name already exists in Cloudflare. This keeps the provisioner simple and avoids ambiguity around name collisions.

**Filtering:** The provisioner should accept an optional list of service names to provision. When provided, only the named services are processed. When omitted, all eligible Pages services are provisioned. This supports the deploy pipeline's per-service deployment.

### Destruction function

A function that deletes all Cloudflare cloud resources tracked in the lock file.

**Behavior:**

- Accept the Cloudflare SDK client, the account ID, and the lock file state as parameters
- Iterate through all resource entries in the lock file:
  - For each D1 database ID: delete via the SDK
  - For each R2 bucket name: delete via the SDK
  - For each KV namespace ID: delete via the SDK
- **Continue on failure:** If an individual deletion fails (API error, resource already gone, permission denied), log the failure and continue with the remaining resources. Do not abort the entire destruction.
- After all deletions have been attempted, remove successfully deleted entries from the lock file. Entries that failed to delete remain in the lock file so the user can retry.
- Return a summary report listing each resource and whether its deletion succeeded or failed

**Scope note:** The destruction function in this step only covers D1, R2, and KV resources. The full `flaregun destroy` command (step 018) orchestrates destruction across all resource types — it calls the sync engine for Access/DNS/redirect cleanup, deletes the tunnel, deletes Pages projects, deletes the fallback Worker, and calls this provisioner's destruction function for D1/R2/KV. This step's destruction function is a focused component, not the full destroy orchestrator.

### Mock client extensions for D1, R2, and KV

Extend the mock Cloudflare SDK client from steps 004/005 to support resource provisioning and destruction.

**New mock capabilities:**

- **D1:** Tracked methods for `d1.database.create` and `d1.database.delete`. An in-memory array of D1 databases. Create adds a new entry with a generated ID and returns a realistic response shape. Delete removes the entry by ID. A `setDatabases()` state manipulation method for test setup.
- **R2:** Tracked methods for `r2.buckets.create` and `r2.buckets.delete`. An in-memory array of R2 buckets. Create adds a new entry and returns a response. Delete removes by name. A `setBuckets()` state manipulation method.
- **KV:** Tracked methods for `kv.namespaces.create` and `kv.namespaces.delete`. An in-memory array of KV namespaces. Create adds a new entry with a generated ID and returns a response. Delete removes by ID. A `setNamespaces()` state manipulation method.

### Tests

**Resource name integration tests:**
- The provisioner uses the shared naming utility from step 005 to derive resource names
- Appending type-specific suffixes to the base name produces valid D1/R2/KV names
- Resource names follow the expected naming convention (domain + service + type suffix)

**Provisioning tests:**
- A service with `database: true` and no existing lock file entry results in a D1 database being created via the SDK
- A service with `database: true` and an existing D1 database ID in the lock file does not create a new database (idempotency)
- A service with `bucket: true` and no lock file entry results in an R2 bucket being created
- A service with `bucket: true` and an existing R2 bucket name in the lock file does not create a new bucket (idempotency)
- A service with `kv: true` and no lock file entry results in a KV namespace being created
- A service with `kv: true` and an existing KV namespace ID in the lock file does not create a new namespace (idempotency)
- A service declaring all three resources (`database`, `bucket`, `kv`) results in all three being created when none are in the lock file
- A service with no cloud resource declarations results in zero provisioning API calls
- Local services (command+port, no dist) are skipped entirely
- Newly created resource IDs are stored in the lock file after provisioning
- Resource names follow the expected naming convention (domain + service derived)
- Provisioning with a service name filter only provisions the named services
- Provisioning with a service name filter where all named services already have lock file entries results in zero API calls

**Destruction tests:**
- Destroying with a lock file containing a D1 database entry results in a delete call for that database ID
- Destroying with a lock file containing an R2 bucket entry results in a delete call for that bucket name
- Destroying with a lock file containing a KV namespace entry results in a delete call for that namespace ID
- Destroying with multiple resource types deletes all of them
- If a single deletion fails, the remaining deletions still proceed (continue on failure)
- Successfully deleted resources are removed from the lock file
- Resources that failed to delete remain in the lock file
- Destroying with an empty lock file results in zero API calls
- The destruction function returns a summary indicating success/failure per resource
