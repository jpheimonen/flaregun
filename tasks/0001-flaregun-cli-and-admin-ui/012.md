# 012: Admin UI backend

## Context

The admin UI backend is a Bun HTTP server that powers the admin dashboard at `admin.yourdomain.com`. It serves the pre-built React SPA (step 014/015) as static files, provides REST endpoints for config management and service control, and exposes a WebSocket endpoint for real-time log streaming from supervised local services.

The backend does not implement its own authentication. It relies on Cloudflare Access — the admin subdomain has an Access application with `admin_only` policy (created by the sync engine in step 004), so only superusers can reach it. The backend is only accessible through the tunnel, never directly exposed.

The backend integrates with two components from previous steps:
- The **process supervisor** (step 011) — the backend queries service states, invokes restart/stop actions, reads log buffers, and subscribes to log streams.
- The **hot-reload engine** (step 013) — the backend triggers hot-reload after a config save, delegating the diff-driven change application to the hot-reload engine.

The backend also integrates with a future component:
- The **admin UI frontend** (steps 014/015) — the backend serves the pre-built SPA and provides the API it consumes.

The admin backend automatically selects an available port at startup. This port is communicated to the orchestrator (step 016) so it can be included in the tunnel ingress rules for the `admin` subdomain.

## Related Code

Existing files/patterns to reference or extend:

- Step 011 (process supervisor) — The backend is a primary consumer of the supervisor's API. It calls: `getServiceState()` / `getAllServiceStates()` for the dashboard, `restart()` / `stop()` for service management, `getLogBuffer()` for initial log history, and `subscribeToLogs()` for WebSocket streaming. The supervisor's subscription mechanism (callback + unsubscribe function) directly maps to the WebSocket connection lifecycle.

- Step 013 (hot-reload engine) — The backend's config save endpoint triggers hot-reload after writing the new config. The hot-reload engine accepts the old and new config, computes the diff, and applies changes. The backend does not need to understand the diff — it delegates entirely to the hot-reload engine and returns the result (success or list of errors) to the frontend.

- Step 002 (config loader) — The backend uses the config loader for two purposes: reading the current config (for the config read endpoint) and validating proposed config changes (for the validate endpoint). The `parseConfig()` function validates YAML and returns either a valid config or a `ConfigValidationError` with the list of errors.

- `../personal-homepage/scripts/up.ts` (lines 153–167) — The `UpDeps` dependency injection interface demonstrates how to make the orchestration layer testable. The admin backend should follow the same pattern: accept the supervisor, hot-reload engine, and config file path as injected dependencies so it can be tested without real processes or files.

## Reuse Opportunities

- **Config loader from step 002** — `parseConfig()` for validation and `loadConfig()` for reading. The validate endpoint calls `parseConfig()` on the proposed YAML and returns either success or the error list. The read endpoint calls `loadConfig()` (or reads the raw YAML file) and returns the contents.

- **Process supervisor API from step 011** — All service state queries and management actions go through the supervisor's programmatic API. No direct process manipulation in the backend.

- **Bun's built-in HTTP server** — Bun provides `Bun.serve()` with native WebSocket support via the `websocket` handler option. This is the right foundation for the backend — a single server instance that handles both HTTP requests and WebSocket upgrades. No external HTTP framework needed.

## Deliverables

### HTTP server with automatic port selection

A Bun HTTP server that starts on an available port and serves both REST endpoints and WebSocket connections.

**Behavior:**

- At startup, attempt to bind to a preferred port. If the port is unavailable, try additional ports until one is found. Report the selected port so the orchestrator can include it in tunnel ingress rules.
- Accept injected dependencies: the process supervisor instance, the hot-reload engine instance, the config file path, and the path to the pre-built SPA directory. The hot-reload engine dependency should be typed as an interface/type that specifies the contract step 013 will implement: a function that accepts the old config, new config, SDK client, lock file state, and process supervisor, and returns a result indicating which changes succeeded and which failed. Define this interface in this step so step 013's implementer knows exactly what to implement, and so tests can provide a mock matching the same contract.
- Provide a `stop()` method that gracefully shuts down the server (used by the orchestrator during shutdown).
- Return the selected port after startup so the orchestrator knows where to route `admin.domain` traffic.

### Static file serving

Serve the pre-built admin UI frontend (React SPA) as static files.

**Behavior:**

- Requests to the root path (`/`) return `index.html` from the SPA directory.
- Requests to paths matching files in the SPA directory (JS bundles, CSS files, images, fonts) return the corresponding file with the appropriate `Content-Type` header.
- Requests to paths that do not match a static file and are not API endpoints return `index.html` (SPA fallback — the frontend handles client-side routing).
- Standard MIME types should be set based on file extension (`.js` → `application/javascript`, `.css` → `text/css`, `.html` → `text/html`, `.json` → `application/json`, etc.).

### REST endpoint: Config read

Returns the current contents of `flaregun.yml`.

**Behavior:**

- **Method/path:** GET on the config endpoint
- Read the config file from disk and return its raw YAML content as a string
- Return a JSON response with the YAML content and a success indicator
- If the config file cannot be read (missing, permission error), return an appropriate error response

### REST endpoint: Config validate

Validates proposed YAML config content without writing to disk.

**Behavior:**

- **Method/path:** POST on the config validate endpoint
- Accept the proposed YAML content in the request body
- Parse and validate it using the config loader's `parseConfig()` function
- If valid, return a success response with no errors
- If invalid, return a response containing the list of validation errors from `ConfigValidationError`
- This endpoint never writes to disk — it is purely for live validation as the user types in the config editor

### REST endpoint: Config save

Writes new config content to disk and triggers hot-reload.

**Behavior:**

- **Method/path:** POST on the config save endpoint
- Accept the new YAML content in the request body
- **Validate first:** Parse and validate the proposed config. If validation fails, return the errors without writing to disk. This prevents saving broken config.
- **Read current config:** Load the current config from disk (the "old" config for diffing).
- **Write to disk:** Write the new YAML content to the config file.
- **Trigger hot-reload:** Pass the old and new parsed configs to the hot-reload engine (step 013). The hot-reload engine computes the diff and applies changes (start/stop services, update Access policies, update ingress rules, etc.).
- **Return result:** Return the hot-reload result to the client — either success or a list of errors from the reload process. Note that even if hot-reload encounters errors, the config has already been saved to disk. The response should indicate which changes succeeded and which failed.

### REST endpoint: Service list

Returns all services with their current runtime states.

**Behavior:**

- **Method/path:** GET on the services endpoint
- Query the process supervisor for all service states
- For each local service: return the service name, subdomain, current lifecycle state (starting/running/crashed/restarting/stopped), uptime, restart count, and last crash reason (if applicable)
- For each Pages service: return the service name, subdomain, and service type indicator. Pages services are not supervised — their status comes from the lock file (deployed/not deployed) rather than the process supervisor.
- Return the combined list as a JSON response

### REST endpoint: Service restart

Restarts a specific local service.

**Behavior:**

- **Method/path:** POST on the service restart endpoint (service name in the path or body)
- Invoke the process supervisor's restart operation for the named service
- If the service exists and is a local service, trigger the restart and return success
- If the service does not exist or is a Pages service (not restartable), return an appropriate error
- The restart operation kills the current process and spawns a new one (handled by the supervisor)

### REST endpoint: Service stop

Stops a specific local service.

**Behavior:**

- **Method/path:** POST on the service stop endpoint (service name in the path or body)
- Invoke the process supervisor's stop operation for the named service
- If the service exists and is a local service, trigger the stop and return success
- If the service does not exist or is a Pages service (not stoppable), return an appropriate error
- The stop operation sends a termination signal and transitions the service to `stopped` (handled by the supervisor)

### WebSocket endpoint: Log streaming

A WebSocket endpoint that streams log output from supervised services in real time.

**Behavior:**

- **Upgrade path:** Requests to the log streaming path with a WebSocket upgrade header are upgraded to WebSocket connections.
- **Subscription model:** After connecting, the client sends a message indicating which service(s) to subscribe to. Two modes:
  - **Per-service:** Subscribe to logs from a specific named service. Only log entries from that service are delivered.
  - **Combined:** Subscribe to logs from all services. Log entries from all services are delivered, tagged with the source service name.
- **Initial history:** Upon subscription, send the current contents of the service's log buffer (from the supervisor's `getLogBuffer()`) so the client sees recent history immediately. Then switch to real-time streaming.
- **Real-time delivery:** Use the supervisor's `subscribeToLogs()` mechanism. Each log entry delivered by the supervisor is forwarded to the WebSocket client as a JSON message containing the timestamp, service name, stream source (stdout/stderr), and log line content.
- **Client disconnect:** When a WebSocket client disconnects, unsubscribe from the supervisor's log stream. This must be clean — no lingering subscriptions, no errors from sending to closed connections.
- **Multiple clients:** Multiple WebSocket clients can be connected simultaneously with different subscriptions. Each client receives only the logs they subscribed to. One client disconnecting does not affect others.
- **Switching subscriptions:** A connected client can send a new subscription message to change which service they are following without disconnecting and reconnecting.

### Tests

The backend tests start a real Bun HTTP server (on a random available port) and make HTTP/WebSocket requests against it. The process supervisor and hot-reload engine are injected as mock/stub implementations.

**Static file serving tests:**
- A request for the root path returns `index.html` with `text/html` content type
- A request for a JS file returns the file with `application/javascript` content type
- A request for a CSS file returns the file with `text/css` content type
- A request for a path that does not match a file or API endpoint returns `index.html` (SPA fallback)

**Config read tests:**
- The config read endpoint returns the current contents of `flaregun.yml` as a string
- If the config file is missing, the endpoint returns an error response

**Config validate tests:**
- Valid YAML config returns a success response with no errors
- Invalid config returns a response containing the list of validation errors
- The validate endpoint does not write anything to disk

**Config save tests:**
- Valid config is written to disk and the hot-reload engine is triggered
- Invalid config is rejected without writing to disk
- The response includes the hot-reload result (success or errors from applying changes)
- After save, the config file on disk contains the new content

**Service list tests:**
- The service list endpoint returns all services with their current states
- Local services include lifecycle state, uptime, and restart count from the supervisor
- Pages services include type and deployment info

**Service management tests:**
- The restart endpoint invokes the supervisor's restart for the named service
- The restart endpoint returns an error for a non-existent service
- The restart endpoint returns an error for a Pages service (not restartable)
- The stop endpoint invokes the supervisor's stop for the named service
- The stop endpoint returns an error for a non-existent service

**WebSocket log streaming tests:**
- A WebSocket client connecting and subscribing to a service receives log entries from that service
- A WebSocket client subscribing to the combined stream receives log entries from all services
- Upon subscription, the client receives recent log history (buffer contents) before real-time entries
- Log entries include timestamp, service name, stream source, and content
- Disconnecting a client does not affect other connected clients
- A client can switch subscriptions by sending a new subscription message

**Port selection tests:**
- The server starts and reports the selected port
- If the preferred port is unavailable, the server selects an alternative port
