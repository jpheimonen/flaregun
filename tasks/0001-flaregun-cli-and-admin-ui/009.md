# 009: Deploy pipeline

## Context

The deploy pipeline is the orchestrator behind `flaregun deploy`. It takes Pages services from config, runs each one through a multi-step deployment sequence (build → scaffold → copy functions → provision resources → generate wrangler config → wrangler deploy → attach custom domain), and separately deploys the fallback Worker. It ties together components built in earlier steps: the resource provisioner (step 006), the functions scaffolder and wrangler config generator (step 007), and the fallback Worker generator (step 008).

The personal-homepage project has a simpler deploy script that handles one Pages project and one Worker sequentially. Flaregun's pipeline generalizes this for multiple Pages services, adds the scaffolding/provisioning/functions-copy phases, supports service filtering (deploy a subset), and runs service deploys in parallel since they are independent.

Each service deploy is independent — a failure in one service does not prevent others from deploying. The pipeline collects per-service results and produces a summary report. The fallback Worker deploy is also independent from Pages service deploys.

The deploy pipeline does not run the sync engine — sync and deploy are separate concerns. Sync manages Access, tunnel, DNS, and redirect rules (runtime infrastructure). Deploy manages Pages projects, cloud resources, and the fallback Worker (deployment infrastructure). The `flaregun deploy` command handler (delivered in this step) calls both — first sync, then deploy.

## Related Code

Existing files/patterns to reference or extend:

- `../personal-homepage/scripts/deploy.ts` — The existing deploy script. Key patterns to adapt:
  - `checkDeployPrerequisites()` (lines 13–32): checks that `wrangler` is on PATH and required env vars are set. Flaregun's environment manager (step 003) handles env var validation, but the wrangler binary check is relevant here.
  - `deployHomepage()` (lines 95–138): demonstrates the try-deploy → create-project-if-missing → retry pattern. Uses `CommandRunner` dependency injection for testability. Detects "project not found" errors from wrangler output to trigger project creation.
  - `deployWorker()` (lines 144–168): runs `wrangler deploy` from the Worker directory. Uses the same `CommandRunner` injection.
  - `deploy()` (lines 172–211): orchestrates prerequisites → prepare → deploy Pages → deploy Worker → summary. Sequential execution, exit 1 on any failure.

- `../personal-homepage/scripts/lib/process.ts` — `runCommand()` and `CommandRunner` type used for invoking wrangler. The deploy pipeline uses the same process utilities from step 001 to run build commands and wrangler.

- Step 006 (resource provisioner) — Called by the pipeline to provision D1/R2/KV resources before generating wrangler configs. The provisioner handles idempotency via the lock file.

- Step 007 (functions scaffolder and wrangler config generator) — Called by the pipeline to scaffold missing `functions/` directories and generate temporary wrangler.toml files with bindings.

- Step 008 (fallback Worker generator) — Called by the pipeline to generate the Worker source. The pipeline writes both the generated source and wrangler.toml to a temporary directory and runs `wrangler deploy` from there.

- Step 001 (process utilities) — `binaryExists()` for checking wrangler availability. `runCommand()` and `CommandRunner` for executing build commands and wrangler CLI.

## Reuse Opportunities

- **CommandRunner injection** — The existing deploy script's pattern of accepting a `CommandRunner` parameter (defaulting to `runCommand`) transfers directly. This enables testing the full deploy pipeline without actually invoking wrangler or running build commands.

- **Project-not-found retry pattern** — The existing `deployHomepage()` tries the deploy, detects "project not found" errors in wrangler's output, creates the project, and retries. This pattern generalizes for all Pages services.

- **Prerequisite checking** — The `binaryExists("wrangler")` check from `checkDeployPrerequisites()` applies to flaregun's deploy pipeline. The env var checks are handled by the environment manager.

- **Temporary directory utilities from step 007** — The wrangler config generator already provides temp directory creation and cleanup. The deploy pipeline uses the same mechanism for both Pages configs and the fallback Worker directory.

## Deliverables

### Per-service deploy function

A function that deploys a single Pages service through the complete deployment sequence.

**Behavior (executed in order):**

1. **Run build command** — If the service config declares a `build` command, execute it via the command runner. If the build command exits with a non-zero code, fail this service's deploy immediately with a descriptive error. If no build command is declared, skip this step.

2. **Scaffold functions** — If the service declares cloud resources (`database`, `bucket`, or `kv`) and the functions source directory does not exist, invoke the functions scaffolder (step 007) to create a starter `functions/` directory. If the functions directory already exists, skip.

3. **Copy functions into dist** — If a `functions/` source directory exists (either pre-existing or just scaffolded), copy its contents into `dist/functions/` within the service's dist output directory. This ensures Pages Functions survive build output wipes. If no functions directory exists and no cloud resources are declared, skip.

4. **Provision cloud resources** — Invoke the resource provisioner (step 006) for this service to create any missing D1/R2/KV resources. The provisioner checks the lock file for idempotency and stores new resource IDs. If the service has no cloud resource declarations, this is a no-op.

5. **Generate wrangler.toml** — Invoke the wrangler config generator (step 007) to produce a temporary wrangler.toml with the correct project name, `pages_build_output_dir`, and D1/R2/KV bindings from the lock file.

6. **Deploy via wrangler** — Run `wrangler pages deploy` using the generated wrangler.toml. If wrangler reports that the Pages project does not exist, create it first (via `wrangler pages project create`) and retry the deploy. This mirrors the existing personal-homepage pattern.

7. **Attach custom domain** — After a successful wrangler deploy, ensure the service's custom subdomain (`subdomain.domain`) is attached to the Pages project. Check the project's existing custom domains via the Cloudflare SDK. If the subdomain is already attached, skip. If not, add it via the Pages project domains API. This step is what makes the service accessible at its subdomain rather than only at the `.pages.dev` URL.

8. **Cleanup** — Remove the temporary wrangler.toml and any other temp files generated for this service.

**Return value:** The function returns a result indicating success or failure, with error details if failed, so the pipeline can aggregate results.

### Fallback Worker deploy function

A function that generates and deploys the fallback Worker.

**Behavior:**

1. **Create temp directory** — Create a temporary directory for the generated Worker files.
2. **Generate Worker source** — Invoke the fallback Worker generator (step 008) to produce the Worker TypeScript source file in the temp directory. If the config specifies a `down_page` custom HTML file, pass its contents to the generator.
3. **Generate wrangler.toml** — Invoke the fallback Worker wrangler config generator (step 007) to produce the Worker's wrangler.toml in the same temp directory.
4. **Deploy via wrangler** — Run `wrangler deploy` from the temp directory.
5. **Store Worker name in lock file** — After successful deployment, store the fallback Worker name in the lock file so that `flaregun destroy` knows what to delete.
6. **Cleanup** — Remove the temp directory.

**Return value:** Success or failure with error details.

### Deploy pipeline orchestrator

The top-level function that deploys all (or filtered) Pages services and the fallback Worker.

**Behavior:**

- Accept the parsed config, lock file state, Cloudflare SDK client, environment credentials, an optional list of service names to filter, and a command runner as parameters
- **Prerequisite check:** Verify that `wrangler` is available on PATH via `binaryExists()`. Fail early with a descriptive error if wrangler is not installed.
- **Identify eligible services:** Filter the config to Pages services only (services with `dist`). If a service name filter is provided, further restrict to only the named services. If a named service does not exist in the config or is not a Pages service, report an error for that name.
- **Deploy services in parallel:** Launch all eligible service deploys concurrently. Each service deploy is independent — a failure in one does not cancel or affect others. Collect results from all deploys.
- **Deploy fallback Worker:** The fallback Worker deploy runs concurrently with service deploys since it is independent. It always runs unless explicitly filtered out (service name filtering applies only to Pages services, not the Worker). When deploying a filtered subset of services, the fallback Worker is still deployed.
- **Produce summary:** After all deploys complete, produce a summary report listing each service and the fallback Worker with its deploy status (success/failure) and any error messages. The summary should be human-readable for console output.
- **Exit status:** The pipeline returns an overall success/failure indicator. It is considered failed if any service or the Worker failed to deploy.

### Shared build-scaffold-copy function

A reusable function that handles the build → scaffold → copy-functions sequence for a single Pages service. This function is used by both the deploy pipeline (this step) and the build command (step 010).

**Behavior:**

- Accept a Pages service config, the lock file state, and a command runner as parameters
- Run the service's build command (if declared) via the command runner. Fail on non-zero exit.
- If the service declares cloud resources and no functions directory exists, invoke the scaffolder (step 007) to create a starter functions directory.
- If a functions directory exists (pre-existing or just scaffolded), copy it into the service's dist/functions/ directory using the functions copy utility (below).
- Return a result indicating success or failure with error details.

The per-service deploy function calls this shared function as its first phase (steps 1–3 of the deploy sequence). Step 010's build command handler calls it directly for each eligible service.

### Functions copy utility

A utility that copies a `functions/` source directory into a service's `dist/functions/` directory.

**Behavior:**

- Accept the functions source path and the dist output path as parameters
- Copy all files and subdirectories from the source `functions/` into `dist/functions/` within the dist directory
- If `dist/functions/` already exists, overwrite its contents (each deploy gets a fresh copy)
- Preserve the directory structure of the source
- This copy ensures that the user's Pages Functions source code survives build tool output wipes — build tools typically clean the dist directory before writing, which would delete functions if they lived inside dist

### Deploy command handler

The command handler invoked when the user runs `flaregun deploy`. This wires together config loading, environment validation, sync, and the deploy pipeline.

**Behavior (executed in order):**

1. **Load and validate config:** Read `flaregun.yml` via the config loader (step 002). If the config is invalid, report the errors and exit.
2. **Load environment:** Validate that the required environment variables are present via the environment manager (step 003). The deploy command requires API token, account ID, and zone ID. It does not require the tunnel token. If required variables are missing, report which ones and suggest `flaregun setup`.
3. **Load lock file:** Load `flaregun.lock` via the lock file manager (step 003). If the file doesn't exist, initialize an empty lock file state (first deploy).
4. **Check prerequisites:** Verify that `wrangler` is available on PATH via `binaryExists()`. Fail early if missing.
5. **Initialize SDK client:** Create the Cloudflare SDK client from the loaded credentials.
6. **Run full sync:** Execute the full sync orchestrator (step 005) to ensure Cloudflare state (Access, DNS, redirect rules) is up to date before deploying. The sync uses the tunnel ID from the lock file if present. If there is no tunnel ID yet (first deploy before `flaregun up`), sync skips the tunnel ingress step and logs a note that tunnel ingress will be configured on first `flaregun up`.
7. **Run deploy pipeline:** Execute the deploy pipeline orchestrator with the parsed config, lock file, SDK client, credentials, optional service name filter from CLI args, and the command runner.
8. **Report results:** Print the deploy summary and exit with code 0 on full success or non-zero on any failure.

**Service name filtering:** `flaregun deploy` accepts optional service names as positional arguments (e.g., `flaregun deploy homepage blog`). When provided, only the named services are deployed. When omitted, all Pages services are deployed. The fallback Worker is always deployed regardless of filtering.

**Dependency injection:** The deploy command handler accepts all subsystem dependencies as injectable parameters, following the same pattern as the orchestrator (step 016) and destroy command (step 018).

### Tests

The deploy pipeline tests use the `CommandRunner` dependency injection to mock all wrangler and build command invocations. They do not actually run wrangler or build anything — they verify the pipeline's orchestration logic.

**Build step tests:**
- A service with a `build` command has that command executed before any other deploy step
- A build command that exits with non-zero code prevents the service's deploy and reports the failure
- A service without a `build` command skips the build step and proceeds to scaffolding

**Scaffolding and functions copy tests:**
- A service with cloud resources and no functions directory triggers the scaffolder before the functions copy
- A service with cloud resources and an existing functions directory skips scaffolding and proceeds to copy
- A service with no cloud resources and no functions directory skips both scaffolding and copying
- Functions are copied from the source directory into `dist/functions/` before wrangler deploy

**Resource provisioning tests:**
- Resource provisioning runs after the build step and before wrangler config generation
- A service with cloud resources invokes the provisioner for those resources
- A service with no cloud resources does not invoke the provisioner

**Wrangler deploy tests:**
- The pipeline runs `wrangler pages deploy` with the generated wrangler.toml
- If wrangler reports a project-not-found error, the pipeline creates the project and retries
- A failed wrangler deploy (non-zero exit, not project-not-found) reports the failure without retrying

**Custom domain attachment tests:**
- After a successful deploy, the service's custom subdomain is attached to the Pages project if not already present
- If the custom subdomain is already attached, no attachment API call is made (idempotency)

**Fallback Worker deploy tests:**
- The fallback Worker source and wrangler.toml are generated in a temp directory
- Wrangler deploy is run from the temp directory
- The fallback Worker name is stored in the lock file after successful deploy
- The temp directory is cleaned up after deploy (success or failure)

**Pipeline orchestrator tests:**
- Deploying with no service filter deploys all Pages services
- Deploying with a service name filter only deploys the named services
- The fallback Worker is deployed regardless of service name filtering
- Multiple service deploys run concurrently (verified by checking that they are launched in parallel, not that they execute simultaneously — the test can verify call ordering or use timing)
- A failure in one service's deploy does not prevent other services from deploying
- The pipeline produces a summary listing each service with its deploy status
- The pipeline reports overall failure if any service or the Worker failed
- The pipeline checks for wrangler availability before starting any deploys

**Shared build-scaffold-copy tests:**
- The shared function runs the build command, then scaffolding check, then functions copy in order
- A build failure prevents scaffolding and copying
- The shared function is callable independently from the deploy pipeline (for step 010 reuse)

**Functions copy tests:**
- Files from the source functions directory are copied into dist/functions/
- Subdirectory structure within functions/ is preserved
- If dist/functions/ already exists, its contents are replaced with the fresh copy

**Deploy command handler tests:**
- The handler loads config, environment, lock file, and checks for wrangler before deploying
- An invalid config aborts before any deploy operations
- Missing environment variables abort with a descriptive error
- A missing wrangler binary aborts with an error
- The handler runs the full sync engine before the deploy pipeline
- When no tunnel ID exists in the lock file, sync skips the tunnel ingress step
- Service name arguments are passed through as a filter to the pipeline
- The handler exits with non-zero when any deploy fails
