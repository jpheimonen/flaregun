# 005: Sync engine: Tunnel ingress, DNS, redirects, and full sync

## Context

This step completes the sync engine by implementing the remaining three sync steps (tunnel ingress, DNS records, redirect rules) and the full sync orchestrator that runs all five steps in dependency order. Steps 004 and 005 together form the complete sync engine — the mechanism that ensures Cloudflare's live state matches the declared `flaregun.yml`.

The personal-homepage project has direct implementations of all three sync steps, and flaregun adapts them with important extensions. Tunnel ingress gains an implicit admin rule and excludes Pages-only services. DNS gains per-Pages CNAME records and removal handling for deleted services. The redirect rule sync transfers nearly unchanged. The full sync orchestrator is new — the existing project runs the five steps sequentially in a single function, but flaregun's orchestrator must additionally update the lock file after each step and accept injected dependencies for testability.

This step also extends the mock Cloudflare SDK client established in step 004 with tunnel, DNS, and redirect operations so all three new sync steps can be tested with the same mock pattern.

## Reuse Opportunities

- **Tunnel ingress logic** — The build-sort-push pattern from `syncTunnelIngress()` transfers directly. The key adaptation is adding the implicit admin subdomain ingress rule (pointing to the admin backend's port) and filtering out Pages-only services (they don't have localhost ports — they are served by Cloudflare Pages, not by the tunnel).

- **DNS record logic** — The wildcard CNAME creation from `syncDnsRecords()` transfers. Flaregun extends this to handle per-Pages-service CNAMEs (each Pages service needs a CNAME for its custom subdomain pointing to its `pages.dev` project) and removal handling (deleting DNS records for services removed from config). The www CNAME logic also adapts — flaregun's version needs to determine which Pages project serves the www subdomain based on config.

- **Redirect rule logic** — The `syncRedirectRule()` approach of reading the existing phase ruleset, checking for a matching expression, and appending if missing transfers nearly unchanged. Only the domain name parameterization changes.

- **Full sync orchestration** — The sequential step ordering from `sync()` transfers, but flaregun's version accepts injected dependencies and writes to the lock file after each successful step.

- **Mock client extensions** — The mock patterns from step 004 (`track()`, in-memory state stores, `mockPageResult()`) extend naturally to tunnel, DNS, and redirect operations. The existing test patterns for these operations (`setDnsRecords()`, `setRedirectRuleset()`, `getCalls("tunnelConfig.update")`) provide the exact mock interface design.

## Deliverables

### Resource naming convention utility

A shared utility function that derives human-readable resource names from the domain and service name. This utility is introduced here because DNS sync needs it to construct Pages project `pages.dev` addresses for per-service CNAME records. It is also reused by the resource provisioner (step 006) for D1/R2/KV naming and by the wrangler config generator (step 007) for Pages project names.

**Behavior:**

- Accept a domain string and a service name string
- Produce a deterministic, human-readable name by combining a domain-derived prefix (dots replaced with hyphens) and the service name
- The generated name must satisfy the constraints of all Cloudflare resource types that use it: R2 bucket naming rules (lowercase, hyphens only, length limits), Pages project naming rules, and D1/KV naming rules
- Different services on the same domain always produce distinct names
- The same domain and service always produce the same name (deterministic)
- A suffix can be appended by callers for resource type disambiguation (e.g., `-db`, `-bucket`, `-kv`) — the utility provides the base name

**Placement:** This utility lives in a shared module (e.g., `src/naming.ts`) so it can be imported by step 005 (DNS sync), step 006 (resource provisioner), and step 007 (wrangler config generator).

### Tunnel ingress sync

A function that pushes the complete set of tunnel ingress rules derived from the current config.

**Behavior:**

- Build an ingress rule for every local service: map `subdomain.domain` → `http://localhost:port`
- Add an implicit ingress rule for the admin UI: map `admin.domain` → `http://localhost:adminPort` (the admin backend port is passed as a parameter or derived from context)
- Do not include Pages services — they are served by Cloudflare Pages via their custom domains, not through the tunnel
- Sort all rules alphabetically by hostname for deterministic ordering
- Append a catch-all rule with empty hostname and `http_status:404` as the last entry
- Push the entire ingress array to the tunnel configuration via `client.zeroTrust.tunnels.cloudflared.configurations.update()` — this is always a full replacement
- The tunnel ID is passed as a parameter (from the lock file or environment)

**Removal handling:** Tunnel ingress handles removals implicitly — because the entire ingress array is rebuilt from the current config and pushed as a replacement, any services removed from config are automatically absent from the next push. No explicit deletion is needed.

### DNS record sync

A function that ensures all required DNS records exist for the current config.

**Behavior:**

- **Wildcard CNAME:** Ensure a `*.domain` CNAME record exists pointing to `tunnelId.cfargotunnel.com`. List existing CNAME records first. If the wildcard already exists with the correct content, skip. If it doesn't exist, create it with `proxied: true` and `ttl: 1` (automatic).
- **Per-Pages CNAME:** For each Pages service in the config, ensure a CNAME record exists for `subdomain.domain` pointing to the Pages project's `pages.dev` address (the project name is derived from the domain and service name using the resource naming convention utility defined above in this step). List existing records and skip if already matching. Create or update if different.
- **www CNAME:** Ensure a `www.domain` CNAME record exists pointing to the appropriate Pages project's `pages.dev` address. If the www record exists but points to the wrong target, update it rather than creating a duplicate.
- All DNS records use `proxied: true` and `ttl: 1` (automatic).
- **Removal handling:** Compare the expected set of CNAME records (derived from current config) against existing CNAME records. For any managed DNS records that correspond to services no longer in the config, delete them via the SDK. The wildcard and www records are not removed by service removal — they are domain-level infrastructure. Only per-service CNAME records for removed Pages services are cleaned up.

### Redirect rule sync

A function that ensures a bare-domain-to-www 301 redirect rule exists.

**Behavior:**

- Construct the redirect expression: `(http.host eq "domain")` where domain comes from the config
- Construct the target URL: `https://www.domain`
- Attempt to read the existing `http_request_dynamic_redirect` phase ruleset via `client.rulesets.phases.get()`. If the phase doesn't exist yet (throws an error), treat it as an empty ruleset.
- Check if any existing rule in the ruleset matches the redirect expression
- If a matching rule already exists, skip (idempotent)
- If no matching rule exists, build the updated rules array: preserve all existing rules (with their IDs) and append the new redirect rule with `action: "redirect"`, `status_code: 301`, the target URL, and `preserve_query_string: true`
- Push the updated rules via `client.rulesets.phases.update()`, using the same type assertion pattern from the existing code to handle the SDK's union type constraints

### Full sync orchestrator

A function that runs all five sync steps in the correct dependency order, tying them together into a single sync operation.

**Behavior:**

- Accept all required dependencies as parameters: the Cloudflare SDK client, the parsed config, the validated credentials (account ID, zone ID, tunnel ID), and the lock file state
- Execute the five steps in order:
  1. **Access applications** — returns the list of managed applications for the policy step
  2. **Access policies** — uses the managed applications from step 1
  3. **Tunnel ingress** — uses the tunnel ID from credentials
  4. **DNS records** — uses the zone ID and tunnel ID from credentials
  5. **Redirect rules** — uses the zone ID from credentials
- After each step that mutates Cloudflare state, save the lock file to persist any new resource IDs
- The redirect rule step should be wrapped in error handling that logs a warning but does not fail the entire sync (following the existing pattern — the zone rulesets permission may not be granted)
- Return a summary indicating which steps were executed and whether each succeeded

### Mock client extensions

Extend the mock Cloudflare SDK client from step 004 to support the three new sync steps.

**New mock capabilities:**

- **Tunnel configuration:** A `tunnelConfig.update` tracked method that accepts the tunnel ID and ingress config. An in-memory store of the current tunnel configuration for state verification if needed.
- **DNS records:** Tracked methods for `dns.records.list`, `dns.records.create`, `dns.records.update`, and `dns.records.delete`. An in-memory array of DNS records. A `setDnsRecords()` state manipulation method for test setup. The list method should return `mockPageResult()` iterables. Create adds to the store with a generated ID. Delete removes from the store.
- **Redirect rulesets:** Tracked methods for `rulesets.phases.get` and `rulesets.phases.update`. An in-memory redirect ruleset object. A `setRedirectRuleset()` state manipulation method for test setup. The get method should throw when no ruleset exists (matching production behavior) or return the stored ruleset. The update method should store the new rules and track the call.
