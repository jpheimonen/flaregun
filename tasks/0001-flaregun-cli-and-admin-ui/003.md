# 003: Lock file manager, environment manager, and SDK client

## Context

This step builds the state management layer that the sync engine, deploy pipeline, and all Cloudflare-interacting commands depend on. Three components are delivered together because they form a cohesive unit: the lock file tracks what resources exist, the environment manager provides credentials, and the SDK client wraps the Cloudflare API. All three must exist before the sync engine (step 004) can be built.

The lock file (`flaregun.lock`) is entirely new — the personal-homepage project has no equivalent because it doesn't track provisioned resource IDs. The environment manager adapts the env validation patterns from `sync.ts` and `up.ts`, but with important changes: variables are loaded from a `.env` file (not assumed to be in `process.env`), the required variable set is context-dependent (tunnel token is only needed for `up`, not `deploy`), and error messages suggest `flaregun setup` when nothing is configured. The SDK client wrapper is a thin layer over the official `cloudflare` package, primarily providing a dependency injection seam so tests can substitute a mock client.

## Related Code

Existing files/patterns to reference or extend:

- `../personal-homepage/scripts/sync.ts` (lines 22–56) — `validateEnv()` function that checks for required `CLOUDFLARE_*` environment variables, collects missing variable names, and throws a descriptive error listing all missing variables. The `SyncEnv` type bundles validated values into a typed object. The Cloudflare SDK client is initialized with `new Cloudflare({ apiToken: env.apiToken })` at line 415.

- `../personal-homepage/scripts/up.ts` (lines 19–64) — `checkPrerequisites()` validates both env vars and binary availability. Includes a hint about the `.env` file in error messages (`"Check your .env file"` vs `"No .env file found"`). Also validates `CLOUDFLARE_TUNNEL_TOKEN` which `sync.ts` does not require.

- `../personal-homepage/scripts/sync.test.ts` (lines 58–130) — `createMockClient()` factory that builds a mock Cloudflare SDK client with call tracking arrays and in-memory state stores. This pattern is critical — the SDK client wrapper must be designed so that tests can inject this mock in place of the real client. The mock tracks calls via a `track()` helper and stores state in plain objects/arrays.

- `../personal-homepage/.env.example` — Documents all five required environment variables with descriptive comments.

## Reuse Opportunities

- **Environment validation pattern** — The `validateEnv()` approach from `sync.ts` (collect missing variable names in an array, throw with all missing at once) transfers directly. Flaregun extends it by loading from a `.env` file first and making some variables context-dependent.

- **SDK client initialization** — The `new Cloudflare({ apiToken })` pattern from `sync.ts` line 415 is the same initialization flaregun will use, just wrapped in a factory function that accepts injected credentials.

- **Mock client pattern** — The `createMockClient()` pattern from `sync.test.ts` establishes how the SDK client seam should work. The real client and mock client must be substitutable. This means the sync engine and resource provisioner should accept the client as a parameter rather than constructing it internally.

- **YAML serialization** — The lock file uses the same `js-yaml` package already in the project dependencies for config parsing. The `load()` and `dump()` functions from `js-yaml` handle both reading and writing.

## Deliverables

### Lock file manager

A module in `src/lock/` that manages the `flaregun.lock` YAML file.

**Data tracked in the lock file:**
- `tunnel` section with the tunnel `id`
- `pages` section mapping service names to their provisioned Pages project data: `project_name`, and optionally `d1_database_id`, `r2_bucket_name`, `kv_namespace_id`
- `access` section mapping service names to their Access application `app_id`
- `worker` section with the fallback Worker `name`

**Operations:**

- **Load:** Read `flaregun.lock` from a given path. If the file does not exist, return an empty state object (first run scenario — no error). If the file exists but contains invalid YAML, throw a descriptive parse error.

- **Save:** Serialize the current state to YAML and write it to disk. The output file should include a header comment indicating it is auto-generated by flaregun and should not be manually edited.

- **Look up:** Given a service name and resource type (e.g., "d1 database"), return the resource ID if it exists in the lock state, or indicate that it does not exist.

- **Store:** Given a service name, resource type, and resource ID, update the in-memory state. The caller is responsible for calling save afterwards.

- **Remove:** Given a service name, clear all that service's entries from the lock state (used when a service is removed from config or during destroy).

- **Clear:** Reset the entire lock state to empty (used by destroy after all resources are deleted).

The load and save functions should accept a file path parameter to support testing with temporary directories. The in-memory state object must never contain secrets — only Cloudflare resource identifiers.

### Environment manager

A module in `src/env/` that loads and validates Cloudflare credentials.

**Loading:** Read the `.env` file co-located with `flaregun.yml` (path derived from the config file path). Parse key-value pairs and make them available. If the `.env` file does not exist, proceed with whatever is already in `process.env` (environment variables may be set externally, e.g., in CI).

**Validation:** Accept a context parameter indicating which command is running, and validate the required variables accordingly:

- `CLOUDFLARE_API_TOKEN` — required for all commands that interact with Cloudflare (everything except `build`)
- `CLOUDFLARE_ACCOUNT_ID` — required for all commands that interact with Cloudflare
- `CLOUDFLARE_ZONE_ID` — required for all commands that interact with Cloudflare
- `CLOUDFLARE_TUNNEL_TOKEN` — required only for the `up` command (needed to start the tunnel daemon)

Collect all missing variables and report them together in a single error message (following the eager collection pattern from `sync.ts`). When no `.env` file exists and no variables are set, the error should suggest running `flaregun setup`.

**Output:** Return a typed credentials object with all validated values, similar to the `SyncEnv` type from `sync.ts`.

### Cloudflare SDK client wrapper

A module in `src/cloudflare/` (or co-located with the env manager) that provides a factory function to create a Cloudflare SDK client.

**Design goals:**
- The factory accepts the validated credentials (API token at minimum) and returns an initialized Cloudflare SDK client
- The factory function provides a dependency injection seam — the sync engine, resource provisioner, and other components accept the client as a parameter rather than creating it internally
- This makes it trivial to substitute the `createMockClient()` pattern from `sync.test.ts` in tests
- The wrapper does not add its own abstraction layer over the SDK — it exposes the raw Cloudflare client object. Its value is centralizing initialization and providing the injection point.

### Tests

**Lock file manager tests:**
- Loading a lock file that does not exist returns empty state without error
- Loading a valid lock file returns all tracked resource IDs correctly
- Saving a lock file writes valid YAML to disk that can be re-loaded
- Roundtrip: save and re-load produces identical state
- Looking up a resource ID for an existing service returns the correct ID
- Looking up a resource ID for a non-existent service returns a "not found" indicator
- Storing a new resource ID updates the in-memory state
- Removing entries for a service clears all that service's resource IDs (Pages project, D1, R2, KV, Access app)
- Clearing the entire state resets to empty
- Loading a lock file with invalid YAML produces a parse error
- The saved lock file contains no environment variable values or secret strings

**Environment manager tests:**
- All required variables present results in successful validation, returning a typed credentials object
- Missing `CLOUDFLARE_API_TOKEN` produces an error naming that specific variable
- Missing `CLOUDFLARE_ACCOUNT_ID` produces an error naming that specific variable
- Missing `CLOUDFLARE_ZONE_ID` produces an error naming that specific variable
- Missing `CLOUDFLARE_TUNNEL_TOKEN` produces an error when the context is `up`
- Missing `CLOUDFLARE_TUNNEL_TOKEN` does NOT produce an error when the context is `deploy`
- Multiple missing variables are all listed in a single error message
- When no `.env` file exists and no variables are set in the environment, the error message suggests `flaregun setup`
- Variables from the `.env` file are loaded and available for validation

Environment tests that modify `process.env` must save and restore the original values after each test (following the save/restore pattern observed in `sync.test.ts`).

**SDK client wrapper tests:**
- The factory function creates a client when given valid credentials
- The returned client is a Cloudflare SDK instance (or satisfies the expected interface for mock substitution)
