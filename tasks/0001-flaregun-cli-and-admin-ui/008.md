# 008: Fallback Worker generator

## Context

The fallback Worker is a domain-specific Cloudflare Worker deployed via a wildcard route that intercepts all subdomain traffic. Its job is to provide graceful degradation when local services are unreachable — instead of showing a Cloudflare error page, it redirects visitors to a friendly "offline" down page. The Worker also passes through traffic for the root domain and www subdomain (handled by Pages) and serves the down page directly on the `down` subdomain.

The personal-homepage project has a hand-written version of this Worker with the domain `heimonen.cc` hardcoded throughout the source and the down page HTML embedded as a string literal. Flaregun's generator produces equivalent source code but as a templated output: the domain name is injected from the config, and the down page HTML can be either a built-in default (themed with the domain name) or a custom HTML file specified by the user.

This step produces the Worker source file. The wrangler.toml for the Worker was already covered in step 007 (wrangler config generator). The deploy pipeline (step 009) handles writing both files to a temporary directory and running `wrangler deploy`.

The existing Worker has a well-tested `handleRequest` function with dependency-injected fetch for testability — this pattern transfers directly to the generated source. The existing test suite (7 describe blocks, 16 test cases) provides a comprehensive blueprint for flaregun's tests, adapted to use a configurable domain name.

## Related Code

Existing files/patterns to reference or extend:

- `../personal-homepage/worker/src/index.ts` — The complete fallback Worker implementation. Contains the routing logic (bare domain passthrough, www passthrough, down subdomain serving, proxy-with-fallback for all other subdomains) and the inline down page HTML. The `handleRequest` function accepts a dependency-injected `originFetch` parameter for testability. The Worker default export wraps `handleRequest` with the global `fetch`. All domain references (`heimonen.cc`, `down.heimonen.cc`) are hardcoded — flaregun's generator must parameterize these.

- `../personal-homepage/worker/src/index.test.ts` — 16 tests across 5 describe blocks covering: pass-through behavior (200, 301, 302, 404 responses forwarded), offline fallback (502, 503, 523 status codes and network errors trigger redirect), down page serving (200 with HTML, no origin fetch, path-agnostic), route safety (www and bare domain never redirected even on 5xx), and unified failure handling (known and unknown subdomains behave identically when origin is down). Test helpers include `makeRequest`, `mockOrigin`, `mockOriginNetworkError`, and `mockOriginPassthrough`.

- `../personal-homepage/worker/wrangler.toml` — The Worker deployment config with name `heimonen-cc-fallback`, wildcard route pattern `*.heimonen.cc/*`, and zone name `heimonen.cc`. Step 007's wrangler config generator produces this structure with the domain parameterized.

## Reuse Opportunities

- **Routing logic** — The `handleRequest` function's routing logic transfers almost verbatim. The only change is replacing hardcoded domain strings with template variables. The conditional flow (bare domain → passthrough, www → passthrough, down → serve HTML, others → proxy-with-fallback) is well-tested and proven.

- **Dependency injection pattern** — The `originFetch` parameter pattern for testability transfers directly. The generated Worker should export `handleRequest` with the same injectable fetch signature so tests can mock the origin.

- **Test patterns** — The existing test helpers (`makeRequest`, `mockOrigin`, `mockOriginNetworkError`, `mockOriginPassthrough`) and test structure transfer directly. Tests need only be parameterized with the configured domain instead of `heimonen.cc`.

- **Down page HTML** — The existing down page HTML serves as the built-in default template. It needs the domain name injected (replacing hardcoded `heimonen.cc` in the title and any domain-specific text) while keeping the same visual design.

## Deliverables

### Routing logic module

The Worker's routing logic (`handleRequest` and its helpers) is implemented as a regular TypeScript module in `src/worker/` that is directly importable and testable. This module is NOT generated — it is a standard source file that accepts the domain name and down page HTML as parameters. The generator (below) composes the full deployable Worker source by importing or inlining this module with the domain-specific values.

**This separation is critical for testability:** Tests import the routing module directly and call `handleRequest` with test values for domain and down page HTML. There is no need to evaluate generated source code, write to temp files, or use dynamic imports. The routing tests are standard unit tests against a standard module.

**Behavior:**

- The module exports a `handleRequest` function that accepts the request, a domain name, down page HTML content, and a dependency-injectable `originFetch` parameter
- The function uses the domain and down page HTML parameters (not hardcoded values) to implement routing
- The module is placed in `src/worker/handler.ts` (or similar) — a standard source file in the project

### Worker source generator

A function that produces the complete TypeScript source code for the deployable fallback Worker.

**Behavior:**

- Accept the domain name and optional down page HTML content as parameters
- Produce a complete, valid TypeScript Worker source file that:
  - Defines the domain and down page HTML as constants using the provided values
  - Imports or inlines the routing logic from the routing module
  - Exports the default Worker fetch handler that delegates to `handleRequest` with the baked-in domain and HTML
- The generated source is what gets deployed to Cloudflare — it is a self-contained Worker with the domain and HTML embedded as constants
- The routing logic from the module must implement the exact behavior from the existing Worker:

**Routing rules (in evaluation order):**

1. **Bare domain** (hostname equals the domain exactly): pass through to origin without modification. The redirect rule (step 005) handles bare-domain-to-www redirection — the Worker does not interfere.
2. **Non-matching domain** (hostname does not end with `.domain`): pass through to origin. This is a safety fallback — the route pattern should prevent this, but the Worker handles it gracefully.
3. **www subdomain**: pass through to origin without modification. Cloudflare Pages handles www traffic. Critically, www traffic must never be redirected to the down page, even if the origin returns a 5xx error.
4. **down subdomain**: serve the embedded down page HTML directly as a 200 response with `text/html; charset=utf-8` content type. No origin fetch is made. This applies regardless of the request path.
5. **All other subdomains** (the proxy-with-fallback rule): attempt to fetch from the origin.
   - If the origin returns a status below 500 (2xx, 3xx, 4xx): pass the response through unmodified, including all headers.
   - If the origin returns a 5xx status: redirect (302) to the down page URL (`https://down.domain`).
   - If the fetch throws (network error, tunnel unreachable): redirect (302) to the down page URL.

### Down page HTML — built-in default

A built-in default down page HTML template that is used when the user does not specify a custom `down_page` in their config.

**Behavior:**

- The default HTML should be a self-contained, single-file HTML page (no external resources) that displays a friendly offline message
- The domain name must be injected into the HTML (in the page title and/or body text) so the page is themed to the user's domain
- The visual design should be clean, minimal, and dark-themed — following the spirit of the existing personal-homepage down page
- The HTML must be valid and render correctly in all modern browsers

### Down page HTML — custom file embedding

When the user specifies a `down_page` field in their flaregun.yml pointing to an HTML file, the generator reads that file's contents and embeds them in the generated Worker source instead of the built-in default.

**Behavior:**

- Read the file at the path specified by the `down_page` config field (relative to the config file location)
- If the file does not exist, throw a descriptive error indicating the custom down page file was not found
- If the file exists, embed its raw contents as the down page HTML constant in the generated source
- The custom HTML is used as-is — flaregun does not inject the domain name into custom HTML (the user is responsible for their own content)
- The custom HTML replaces only the HTML content — the routing logic remains identical

### Generated source placement

The generator writes the source file to a temporary directory (the same directory where step 007's wrangler config generator writes the Worker's wrangler.toml). The deploy pipeline (step 009) handles the lifecycle of this temporary directory.

**Behavior:**

- Accept a target directory path as a parameter (provided by the deploy pipeline)
- Write the generated TypeScript source file to that directory with a predictable filename
- The filename must match what step 007's wrangler config generator sets as the `main` entry point in the Worker's wrangler.toml
- Return the path to the written file

### Tests

The tests for this step have two concerns: testing the generator itself (does it produce correct source?) and testing the routing logic module (does the Worker behave correctly?). The routing tests import the `handleRequest` function directly from the routing module — no generated code execution, no eval, no dynamic imports. The routing module is a standard importable TypeScript module.

**Generator tests:**

- The generated source contains the configured domain name (not a hardcoded domain)
- The generated source does not contain any hardcoded domain references from the personal-homepage project
- When no custom down_page is provided, the built-in default HTML is embedded
- When a custom down_page file path is provided and the file exists, its contents are embedded
- When a custom down_page file path is provided but the file does not exist, the generator throws a descriptive error
- The built-in default HTML contains the domain name from config
- The generated source is valid TypeScript (exports `handleRequest` and the default fetch handler)

**Pass-through behavior tests (routing rule validation):**

- A request to the bare domain passes through to the origin and returns the origin's response unmodified
- A request to the www subdomain passes through to the origin and returns the origin's response unmodified
- An origin 200 response for a configured subdomain is passed through with the same status, body, and headers
- An origin 301 redirect for a configured subdomain is passed through unmodified
- An origin 302 redirect for a configured subdomain is passed through unmodified
- An origin 404 response for a configured subdomain is passed through (4xx is not a server error)

**Offline fallback tests:**

- An origin 502 response for a non-www/non-bare subdomain triggers a 302 redirect to the down page URL
- An origin 503 response triggers a 302 redirect to the down page URL
- An origin 523 response (origin unreachable) triggers a 302 redirect to the down page URL
- A network error (fetch throws) for a non-www/non-bare subdomain triggers a 302 redirect to the down page URL

**Down page serving tests:**

- A request to the `down` subdomain returns 200 with `text/html; charset=utf-8` content type
- A request to the `down` subdomain returns the embedded HTML content
- A request to the `down` subdomain does not make any fetch to the origin
- A request to the `down` subdomain with any path still serves the down page (path-agnostic)

**Route safety tests:**

- The www subdomain is NOT redirected to the down page even when the origin returns a 5xx error — the 5xx is passed through
- The bare domain is NOT redirected to the down page even when the origin returns a 5xx error — the 5xx is passed through
- A known subdomain and an unknown subdomain produce identical redirect behavior when the origin is unreachable
