# 015: Admin UI frontend: config editor and log viewer

## Context

This step completes the admin UI frontend by implementing the remaining two major views: the config editor and the log viewer. Together with the service dashboard from step 014, these form the complete admin experience at `admin.yourdomain.com`.

The **config editor** lets the user edit `flaregun.yml` directly in the browser. It provides live validation — as the user types, the frontend sends the current YAML to the backend's validate endpoint and shows errors inline, before the user even clicks save. Saving triggers hot-reload (step 013) so changes take effect immediately without restarting `flaregun up`.

The **log viewer** provides real-time log tailing for local services via WebSocket. It connects to the backend's WebSocket endpoint (step 012), subscribes to per-service or combined log streams, and renders log lines as they arrive. It supports auto-scrolling with a pause mechanism so the user can read older output without being pulled to the bottom.

Both views build on the project infrastructure established in step 014 (React + Zustand + MUI, build tooling, application shell, routing).

## Related Code

Existing files/patterns to reference or extend:

- Step 014 (admin UI frontend setup) — The application shell, routing, Zustand store pattern, and MUI theme are already in place. This step adds two new views and their corresponding stores to the existing structure.

- Step 012 (admin UI backend) — The backend API contract defines the endpoints the frontend consumes:
  - Config read endpoint (GET) — returns the current YAML content as a string
  - Config validate endpoint (POST) — accepts YAML, returns validation success or error list
  - Config save endpoint (POST) — accepts YAML, validates, writes to disk, triggers hot-reload, returns result with success/failure per change
  - WebSocket log streaming endpoint — upgrade-based connection, subscription messages for per-service or combined streams, log entries delivered as JSON with timestamp/service/source/content

- Step 013 (hot-reload engine) — The save response includes the hot-reload result: which changes succeeded and which failed. The config editor needs to display this feedback to the user.

## Reuse Opportunities

- **Zustand store pattern from step 014** — The service store pattern (fetch on init, poll for updates, actions calling backend endpoints) applies to the config store (fetch on mount, validate on change, save action).

- **MUI components from step 014** — The component library is already set up. The config editor can use MUI's layout components (Paper, Card, Alert for errors, Button for save). The log viewer can use MUI's typography and layout components for the log output area.

- **Application shell from step 014** — Both new views plug into the existing navigation and layout. No shell changes needed unless the navigation needs additional entries.

## Deliverables

### Zustand store: config editor

A Zustand store that manages the config editor's state.

**Behavior:**

- **Load on mount:** When the config editor view mounts, fetch the current `flaregun.yml` content from the backend's config read endpoint. Store the raw YAML string.
- **Track edits:** Store the current editor content as the user types. Track whether the content has been modified from the loaded version (dirty state).
- **Live validation:** When the editor content changes, send the current YAML to the backend's validate endpoint after a debounce delay (e.g., 300–500ms after the user stops typing). Store the validation result — either no errors or a list of error strings. Clear previous errors when a new validation starts. Do not validate on every keystroke — use the debounce to batch rapid edits.
- **Save action:** Send the current editor content to the backend's config save endpoint. Store the save result (success with hot-reload details, or validation errors). After a successful save, update the "last loaded" content to the saved content (clear dirty state). If the save fails due to validation, show the errors. If the save succeeds but hot-reload has partial failures, show both the success and the failure details.
- **Discard action:** Reset the editor content to the last loaded version, clearing any edits and validation errors.

### Config editor view

A YAML text editor with live validation and save functionality.

**Behavior:**

- **Editor area:** A text editing area that displays the YAML content. The editor should provide a reasonable editing experience for YAML — at minimum, a monospace font, adequate size for editing multi-line configs, and basic text editing capabilities. If a YAML-aware code editor component is available (e.g., CodeMirror, Monaco), it may be used for syntax highlighting and better editing ergonomics, but a plain textarea with monospace styling is also acceptable.
- **Live validation errors:** Validation errors from the debounced validate call are displayed inline below the editor or in a dedicated error panel. Each error from the `ConfigValidationError` error list is shown as a separate item. Errors update as the user edits — they appear when validation detects issues and disappear when the issues are fixed.
- **Save button:** A prominent button that saves the current content. The button:
  - Is disabled when the content has not been modified (not dirty)
  - Is disabled when validation errors are present (prevent saving known-bad config)
  - Shows a loading/pending state during the save API call
  - After a successful save with successful hot-reload, shows a success confirmation (e.g., a toast, snackbar, or inline success message)
  - After a save where hot-reload encountered errors, shows a mixed result: the config was saved, but some changes failed to apply. Display the specific errors from the hot-reload result.
  - After a save that failed validation (should not happen if the button is disabled on errors, but as a safeguard), shows the validation errors.
- **Discard button:** A secondary button that reverts unsaved changes. Disabled when the content has not been modified. Resets the editor to the last saved/loaded content and clears validation errors.
- **Dirty indicator:** A visual cue that unsaved changes exist (e.g., a dot on the tab, "unsaved changes" text, or the discard button becoming enabled). This helps the user know whether they have pending edits.

### Zustand store: log viewer

A Zustand store that manages the log viewer's WebSocket connection and log entries.

**Behavior:**

- **Connection management:** When the log viewer view mounts, open a WebSocket connection to the backend's log streaming endpoint. When the view unmounts (user navigates away), close the connection cleanly.
- **Service selection:** Track which service the user is currently viewing. Support two modes:
  - **Per-service:** Subscribe to a single named service. Only log entries from that service are stored and displayed.
  - **Combined:** Subscribe to all services. Log entries from all services are stored, each tagged with the source service name.
- **Log entry storage:** Store received log entries in an array. Each entry contains the timestamp, service name, stream source (stdout/stderr), and log line content. Cap the stored entries at a reasonable maximum (e.g., 1000–5000 lines) to prevent unbounded memory growth in the browser — evict oldest entries when the limit is reached.
- **Subscription switching:** When the user selects a different service (or switches to/from combined mode), send a new subscription message over the existing WebSocket connection. Clear the current log entries and receive fresh initial history from the backend for the new subscription.
- **Connection status:** Track whether the WebSocket is connected, disconnected, or reconnecting. If the connection drops, attempt automatic reconnection with a short delay.

### Log viewer view

A real-time log output view with service selection and auto-scroll.

**Behavior:**

- **Service selector:** A dropdown, tab bar, or similar control that lets the user choose which service's logs to view. Options include each local service by name plus a "Combined" / "All services" option. Pages services are not shown (they are not supervised and have no log output). Selecting a service switches the WebSocket subscription and clears the displayed logs.
- **Log output area:** A scrollable area that displays log lines. Each log entry shows:
  - **Timestamp** — formatted in a concise, readable format (e.g., `HH:MM:SS` or `HH:MM:SS.mmm`)
  - **Service name** — shown in combined mode to distinguish which service produced the line. In per-service mode, the service name can be omitted or shown more subtly since it's obvious from the selection.
  - **Stream source** — visual differentiation between stdout and stderr (e.g., stderr in a different color like red or orange, stdout in the default color)
  - **Content** — the actual log line text, displayed in a monospace font
- **Auto-scroll:** The log output area automatically scrolls to the bottom as new entries arrive, so the user always sees the latest output. However:
  - If the user manually scrolls up (away from the bottom), auto-scroll pauses. The user can read older output without being pulled back to the bottom.
  - A visual indicator shows when auto-scroll is paused and new entries are arriving below the current scroll position (e.g., a "New logs ↓" button or badge at the bottom).
  - Clicking the indicator or scrolling back to the bottom resumes auto-scroll.
- **Empty state:** When no logs are available (service just started, or no service selected), show an appropriate empty state message.
- **Connection indicator:** Show the WebSocket connection status in the log viewer (connected/disconnected/reconnecting). If disconnected, show a message indicating that log streaming is temporarily unavailable.

### Tests

Frontend tests use the same **Vitest + jsdom + React Testing Library** setup established in step 014. Backend API calls are mocked with `vi.fn()` or `msw`. WebSocket connections are mocked using a fake WebSocket implementation that simulates message delivery.

**Config editor store tests:**
- Loading the config editor fetches the current YAML from the config read endpoint
- Editing the content sets the dirty state to true
- After a debounce delay, changed content triggers a validate call to the backend
- Validation errors from the backend are stored and accessible
- Fixing a validation error and waiting for debounce clears the errors
- The save action calls the config save endpoint with the current content
- A successful save clears the dirty state
- A failed save (validation errors) stores the errors and keeps dirty state
- The discard action resets content to the last loaded version and clears errors

**Config editor view tests:**
- The editor loads and displays the current YAML content from the backend
- Editing the YAML to introduce a validation error shows the error inline after the debounce
- Editing the YAML to fix the error clears the error display after the debounce
- The save button is disabled when the content is not modified
- The save button is disabled when validation errors are present
- Clicking save shows a loading state and then a success or error result
- The discard button reverts to the last loaded content
- A dirty indicator is visible when unsaved changes exist

**Log viewer store tests:**
- Mounting the log viewer opens a WebSocket connection
- Unmounting the log viewer closes the WebSocket connection
- Receiving log entries from the WebSocket adds them to the store
- The log entry buffer does not exceed the maximum size (oldest entries evicted)
- Switching services sends a new subscription message and clears stored entries
- A dropped connection sets the status to disconnected and attempts reconnection

**Log viewer view tests:**
- The service selector shows all local services and a combined option
- Selecting a service switches the displayed logs
- Log entries display with timestamp, stream source differentiation, and content
- In combined mode, log entries display the service name
- Auto-scroll is active when the user is at the bottom of the output
- Scrolling up pauses auto-scroll
- A "new logs" indicator appears when auto-scroll is paused and new entries arrive
- Clicking the indicator or scrolling to the bottom resumes auto-scroll
- An empty state message is shown when no logs are available
