# 011: Process supervisor

## Context

The process supervisor manages the lifecycle of local services during `flaregun up`. Each local service (those with `command` + `port`) runs as a child process spawned and monitored by the supervisor. The supervisor handles crash detection, automatic restart with exponential backoff, stdout/stderr capture for log streaming, and graceful shutdown.

The personal-homepage project has a rudimentary version of this: `launchService()` spawns a process, races a 500ms timer against process exit for immediate crash detection, and returns. There is no restart logic, no state machine, no log capture buffer, and shutdown is a simple `.kill()` on all tracked processes. Flaregun replaces this with a proper supervisor that tracks per-service lifecycle states, implements configurable restart policies, and provides the API surface that the admin UI backend (step 012) and hot-reload engine (step 013) need to manage services dynamically.

The supervisor is a critical piece of the runtime architecture. It is consumed by three other components:
- The **orchestrator** (step 016) starts and stops services via the supervisor during `flaregun up` / `flaregun down`.
- The **admin UI backend** (step 012) queries service states and invokes restart/stop actions via the supervisor.
- The **hot-reload engine** (step 013) starts/stops services when the config changes.

## Reuse Opportunities

- **Spawn and immediate crash detection** — The `launchService()` pattern of racing a timeout against `proc.exited` transfers as the core of the supervisor's spawn behavior. The timer window and race logic adapt directly.

- **Bun.spawn() API** — The supervisor uses the same `Bun.spawn()` API as the existing code, but with `stdout: "pipe"` and `stderr: "pipe"` instead of `"inherit"` to capture output into the rolling buffer.

## Deliverables

### Service lifecycle state machine

Each supervised service tracks its lifecycle through a set of well-defined states with deterministic transitions.

**States:**
- **starting** — The process has been spawned but has not yet survived the initial stability window. This is the initial state when a service is started.
- **running** — The process survived the initial window and is considered stable. Uptime tracking begins (or resumes) from this transition.
- **crashed** — The process exited unexpectedly. The supervisor records the crash and prepares for a restart (unless max retries exceeded).
- **restarting** — The supervisor is waiting through the backoff delay before spawning a new process. After the delay, it transitions back to `starting`.
- **stopped** — The service has been intentionally stopped (by the user, by max retries being exceeded, or by shutdown). It will not be restarted automatically.

**Transitions:**
- `starting` → `running`: Process survives the initial stability window
- `starting` → `crashed`: Process exits during the initial stability window
- `running` → `crashed`: Process exits unexpectedly
- `crashed` → `restarting`: Max retries not exceeded, preparing for restart
- `crashed` → `stopped`: Max retries exceeded
- `restarting` → `starting`: Backoff delay elapsed, respawning
- `running` → `stopped`: Explicit stop requested (user action or shutdown)
- `starting` → `stopped`: Explicit stop requested during startup

**Per-service state tracking:**
- Current state
- Uptime (time since last transition to `running`, reset on each restart)
- Restart count (number of times the service has been restarted since the supervisor started managing it)
- Last crash reason (exit code or error message from the most recent crash)

### Process spawning

The supervisor spawns each service's command as a child process.

**Behavior:**

- Parse the service's `command` string into an executable and arguments (split on whitespace)
- Spawn using `Bun.spawn()` with stdout and stderr set to piped mode (not inherited) so the supervisor can capture output
- After spawning, enter the **initial stability window** — race a short timer (e.g., 500ms, matching the existing pattern) against the process exiting. The stability window duration should be configurable (injectable) so tests can use a shorter value (e.g., 50ms) to avoid slow test suites
- If the process exits before the timer fires, transition to `crashed` — this counts as an immediate crash. Record the exit code.
- If the timer fires before the process exits, transition to `running` — the process is considered stable
- While the process is running, monitor its exit event. When the process exits unexpectedly (state was `running`), transition to `crashed`.

### Exponential backoff restart

When a service crashes, the supervisor automatically restarts it after a delay that increases with consecutive crashes.

**Behavior:**

- After transitioning to `crashed`, check whether `max_retries` is configured for this service and whether the retry count has been exceeded
- If max retries exceeded, transition to `stopped` — no more automatic restarts
- If max retries not exceeded (or not configured, meaning infinite retries), transition to `restarting`
- Wait for the backoff delay before spawning. The delay follows an exponential curve: each consecutive crash increases the delay (e.g., 1s, 2s, 4s, 8s, up to a reasonable cap)
- After the delay, transition to `starting` and spawn a new process
- Increment the restart count
- **Backoff reset:** When a service transitions from `starting` to `running` and remains in the `running` state for a sustained period (e.g., 30 seconds), reset the consecutive crash counter. This means a service that crashes, restarts, runs successfully for a while, then crashes again starts back at the shortest backoff delay. The sustained period duration should be configurable (injectable) so tests can use a shorter value (e.g., 500ms) without waiting 30+ seconds

### Rolling log buffer

The supervisor captures stdout and stderr from every child process and stores the output in a per-service rolling buffer.

**Behavior:**

- Each service has its own log buffer with a bounded maximum size (measured in number of log entries or total bytes — implementer's choice)
- When output arrives on a child process's stdout or stderr stream, the supervisor creates a log entry containing the timestamp, the stream source (stdout/stderr), and the log line content
- Log entries are appended to the service's buffer
- When the buffer reaches its maximum size, the oldest entries are evicted to make room for new ones (ring buffer / circular buffer behavior)
- The buffer contents are queryable — the admin UI backend (step 012) reads the buffer to show recent log history when a client connects
- The supervisor also exposes a subscription mechanism — the admin UI backend's WebSocket handler (step 012) subscribes to log events for real-time streaming. When a new log entry is added, all subscribers for that service are notified with the entry.

**Design notes:**
- Log entries should carry enough metadata for the admin UI to distinguish between stdout and stderr (e.g., for color-coding)
- The subscription mechanism should support per-service subscriptions and a combined "all services" subscription
- The buffer size should be configurable (with a sensible default) but does not need to be exposed in `flaregun.yml` — it is an internal implementation detail

### Service management API

The supervisor exposes a programmatic API for managing individual services. This API is consumed by the admin UI backend (step 012) and the hot-reload engine (step 013).

**Operations:**

- **Start a service:** Begin supervising a service (spawn it, enter the state machine). Used by the orchestrator during startup and by the hot-reload engine when a new service is added to the config.
- **Stop a service:** Send a termination signal to the service's process, wait for graceful exit, force-kill if the timeout elapses, transition to `stopped`. Used by the admin UI and by the hot-reload engine when a service is removed from config.
- **Restart a service:** Stop the current process (if running) and start a new one. Reset the restart count and backoff state. Used by the admin UI.
- **Get service state:** Return the current lifecycle state, uptime, restart count, and last crash reason for a specific service. Used by the admin UI for the dashboard.
- **Get all service states:** Return states for all supervised services. Used by the admin UI for the dashboard view.
- **Get log buffer:** Return the current contents of a service's log buffer. Used by the admin UI when a log viewer connects to show recent history.
- **Subscribe to logs:** Register a callback that receives log entries in real time. Returns an unsubscribe function. Used by the admin UI's WebSocket handler.

### Graceful shutdown

When the supervisor is asked to shut down (SIGINT/SIGTERM or explicit `flaregun down`), it performs a coordinated stop of all supervised services.

**Behavior:**

- Send a termination signal (SIGTERM) to all child processes simultaneously
- Wait for all processes to exit within a configurable graceful timeout (e.g., 5 seconds)
- After the timeout, force-kill (SIGKILL) any processes that have not yet exited
- Transition all services to `stopped`
- The shutdown function returns (or resolves) once all processes are confirmed terminated
- During shutdown, the supervisor does not restart any crashed processes — automatic restart is disabled

### Tests

Testing the process supervisor requires spawning real (but trivial) child processes. Use simple commands that are guaranteed to be available in the test environment (e.g., `sleep`, `echo`, `cat`, shell scripts) to test lifecycle behavior. For log capture tests, use commands that produce known output on stdout/stderr.

**Lifecycle state machine tests:**
- Starting a service transitions it to `starting`, then to `running` after surviving the initial stability window
- A process that exits immediately after spawn (within the stability window) transitions to `crashed`
- A process that exits while in the `running` state transitions to `crashed`
- A crashed service with retries remaining transitions to `restarting`, then back to `starting` after the backoff delay
- A crashed service with `max_retries` exceeded transitions to `stopped` and is not restarted
- A service with no `max_retries` configured restarts indefinitely (tested with a small number of crashes)
- An explicitly stopped service transitions to `stopped` regardless of its previous state

**Exponential backoff tests:**
- The backoff delay increases with each consecutive crash (verify that each delay is longer than the last)
- The backoff delay is capped at a maximum value (does not grow without bound)
- The backoff counter resets after a service runs successfully for the sustained period
- After a backoff reset, the next crash uses the initial (shortest) delay

**Log capture tests:**
- Stdout output from a child process appears in the service's log buffer with stdout source marker
- Stderr output from a child process appears in the service's log buffer with stderr source marker
- Log entries include timestamps
- The log buffer does not grow beyond its bounded size — oldest entries are evicted when full
- Log entries are delivered to subscribers in real time as they arrive
- Multiple subscribers to the same service each receive the same log entries
- Unsubscribing stops delivery of log entries to that subscriber

**Service management tests:**
- Stopping a running service sends a termination signal and transitions to `stopped`
- Stopping an already-stopped service is a no-op
- Restarting a running service kills the current process and spawns a new one
- Restarting a service resets the restart count and backoff state
- Service state queries return the current state, uptime, and restart count
- Getting the log buffer returns the current buffer contents for the service

**Concurrent supervision tests:**
- Multiple services can be supervised simultaneously and independently
- A crash in one service does not affect other services
- Stopping one service does not affect other services

**Graceful shutdown tests:**
- Shutdown sends a termination signal to all supervised processes
- Processes that exit within the graceful timeout are not force-killed
- Processes that do not exit within the graceful timeout are force-killed
- After shutdown, all services are in the `stopped` state
- During shutdown, crashed services are not restarted
