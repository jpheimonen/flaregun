# 010: Build command

## Context

The build command (`flaregun build`) runs build commands for Pages services locally without deploying anything to Cloudflare. It is useful for CI pipelines, pre-deploy validation, and local development — verifying that all services build successfully before committing to a deploy.

The build command performs a subset of the deploy pipeline's per-service sequence: it runs the build command, scaffolds missing `functions/` directories for services with cloud resources, and copies `functions/` into `dist/functions/`. It does not provision cloud resources, generate wrangler configs, or run wrangler — those are deploy-only concerns.

Like the deploy command, the build command accepts an optional list of service names to build a subset (e.g., `flaregun build homepage blog`). When no names are given, it builds all eligible services. Each service build is independent — a failure in one does not prevent others from building.

Importantly, the build command does not require Cloudflare credentials. It only runs local build commands and file operations, so it works without a `.env` file. This makes it suitable for CI environments where API tokens may not be available.

## Related Code

Existing files/patterns to reference or extend:

- Step 009 (deploy pipeline) — The deploy pipeline's per-service sequence includes the same build → scaffold → copy-functions steps as the build command. The build command should reuse the same underlying functions rather than reimplementing them. Specifically, the build step execution, the scaffolding trigger logic, and the functions copy utility from step 009 are shared.

- Step 007 (functions scaffolder) — The scaffolder is invoked by the build command for services that declare cloud resources but lack a `functions/` directory. The trigger conditions are identical to the deploy pipeline: scaffold if cloud resources declared and functions directory missing.

- Step 009 (functions copy utility) — The utility that copies `functions/` into `dist/functions/` is shared between the build command and the deploy pipeline.

- Step 001 (process utilities) — `runCommand()` and `CommandRunner` type for executing build commands. The same dependency injection pattern enables testing without running real build commands.

- Step 001 (CLI entry point) — The build command is dispatched by the CLI entry point. The CLI passes any trailing arguments as a service name filter array (e.g., `flaregun build homepage blog` → `["homepage", "blog"]`).

- Step 002 (config loader) — The build command loads and validates `flaregun.yml` to determine which services exist and their build configurations. No lock file or environment loading is needed.

## Reuse Opportunities

- **Shared build-scaffold-copy sequence** — The build → scaffold → copy-functions steps are identical between the build command and the deploy pipeline. These should be factored into shared functions that both commands call. The deploy pipeline calls them as part of its larger sequence; the build command calls them as the entire operation. This avoids duplicating the scaffolding trigger logic, the functions copy logic, and the build execution logic.

- **CommandRunner injection** — The same testability pattern from the deploy pipeline: accept a `CommandRunner` parameter for build command execution, enabling tests to mock all subprocess invocations.

- **Per-service result aggregation** — The build command collects per-service results (success/failure with details) and produces a summary, similar to the deploy pipeline's summary. The result type and summary formatting could be shared.

## Deliverables

### Build command handler

The command handler invoked when the user runs `flaregun build [service-names...]`.

**Behavior:**

- Load and validate `flaregun.yml` via the config loader (step 002). If the config is invalid, fail with the validation errors.
- **No credentials required.** The build command does not load `.env` or initialize the Cloudflare SDK client. It only performs local operations.
- **Identify eligible services:** Select all Pages services from the config (services with `dist`). If service name arguments are provided, further filter to only those names.
  - If a named service does not exist in the config, report an error for that name but continue building the others.
  - If a named service exists but is a local service (not Pages), it is still eligible if it has a `build` field — the build command runs its build command. Local services without a `build` field are skipped with a note.
- **Execute per-service build** (for each eligible service, in sequence or parallel — see below):
  1. **Run build command:** If the service declares a `build` command, execute it via the command runner from the service's working directory. If the command exits non-zero, record this service as failed with the error output and move to the next service. If no `build` command is declared, skip this step (the service has no build phase).
  2. **Scaffold functions:** If the service declares cloud resources (`database`, `bucket`, or `kv`) and the functions source directory does not exist, invoke the functions scaffolder (step 007). If the functions directory already exists, skip.
  3. **Copy functions into dist:** If a `functions/` source directory exists (pre-existing or just scaffolded), copy its contents into `dist/functions/` within the service's dist output directory using the functions copy utility from step 009. If no functions directory exists and no cloud resources are declared, skip.
- **Report results:** After all services have been processed, print a per-service summary showing which services built successfully, which were skipped, and which failed (with error details).
- **Exit code:** Exit with code 0 if all services succeeded or were skipped. Exit with a non-zero code if any service's build command failed.

### Shared build-scaffold-copy function

A reusable function that encapsulates the build → scaffold → copy-functions sequence for a single service. Both the build command and the deploy pipeline (step 009) call this function.

**Behavior:**

- Accept the service config, the project root, and a command runner as parameters
- Execute the three steps in order: run build command (if declared), scaffold functions (if needed), copy functions into dist (if present)
- Return a result indicating success, skip (no build command), or failure (with error details)
- This function is the single point of truth for how a service is built — any change to the build sequence is made here and automatically affects both `flaregun build` and `flaregun deploy`

**Design note:** Steps 009 and 010 share this function. Whether it is factored out during step 009 and reused by step 010, or factored out during step 010 as a refactor, is an implementation detail. The key requirement is that by the end of step 010, both commands use the same shared function.

### Tests

Tests use the `CommandRunner` dependency injection to mock build command execution. File system operations (scaffolding, copying) can be tested against a temporary directory.

**Service selection tests:**
- Building with no service name filter selects all Pages services from the config
- Building with a service name filter only builds the named services
- A named service that does not exist in the config produces an error for that name but does not prevent other services from building
- A local service with a `build` field is eligible for building when named explicitly
- A local service without a `build` field is skipped with a note when named explicitly

**Build execution tests:**
- A service with a `build` command has that command executed via the command runner
- The build command runs from the service's working directory
- A build command that exits with a zero code is recorded as success
- A build command that exits with a non-zero code is recorded as failure with the error output
- A service with no `build` command is skipped without error
- A build failure for one service does not prevent building other services

**Scaffolding and functions copy tests:**
- After a successful build, a service with cloud resources and no functions directory triggers the scaffolder
- After a successful build, a service with an existing functions directory has it copied into dist/functions/ without scaffolding
- After a successful build, a service with no cloud resources and no functions directory does not scaffold or copy anything
- Scaffolding and copying do not occur if the build step failed (the sequence stops on build failure)

**Summary and exit code tests:**
- The command reports per-service results (success, skipped, or failure)
- The command exits with code 0 when all services succeed or are skipped
- The command exits with a non-zero code when any service's build fails
- The command works without a `.env` file (no Cloudflare credentials required)

**Shared function tests:**
- The shared build-scaffold-copy function is used by both the build command and the deploy pipeline (this can be verified structurally — both import the same function)
- The shared function handles all three steps in the correct order
