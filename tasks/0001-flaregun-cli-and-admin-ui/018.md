# 018: Destroy command

## Context

The destroy command (`flaregun destroy`) is a one-shot teardown operation that deletes all Cloudflare resources managed by flaregun. It is the inverse of the setup/deploy/sync lifecycle — where `setup` creates credentials and a tunnel, `deploy` provisions cloud resources and deploys code, and `up` syncs Access/DNS/ingress state, `destroy` removes all of it. After running `destroy`, the domain's Cloudflare configuration is clean — no tunnel, no Access applications, no DNS records, no Pages projects, no cloud resources, no fallback Worker.

This is a destructive, irreversible operation. There is no "undo" — deleted D1 databases lose their data, deleted R2 buckets lose their objects, and deleted Pages projects lose their deployment history. The command requires explicit confirmation before proceeding: the user must type the domain name to confirm they understand what they are destroying.

The personal-homepage project has no destroy command — teardown was done manually through the Cloudflare dashboard. Flaregun automates the full teardown, but the critical design constraint is resilience: the command must handle partial failures gracefully. If deleting one resource fails (API error, permission issue, resource in use), the command continues deleting everything else and reports a summary of what succeeded and what failed. The lock file is updated to remove only successfully deleted entries, so a subsequent `destroy` run can retry the failures.

## Related Code

Existing files/patterns to reference or extend:

- Step 003 (lock file manager) — The lock file is the primary input for the destroy command. It contains every Cloudflare resource ID that flaregun has provisioned: tunnel ID, Access application IDs (per service), Pages project names (per service), D1 database IDs, R2 bucket names, KV namespace IDs, and the fallback Worker name. The destroy command reads the lock file to know what to delete, and writes it back after each deletion category to remove successfully deleted entries. The lock file manager's `remove()` and `clear()` operations are used to clean up entries.

- Step 003 (environment manager) — The destroy command requires Cloudflare credentials (API token, account ID, zone ID) but does not need the tunnel token. The environment manager validates that the required variables are present before proceeding.

- Step 003 (SDK client wrapper) — The destroy command creates a Cloudflare SDK client from the loaded credentials to make deletion API calls. The same client wrapper and dependency injection pattern used by the sync engine and resource provisioner applies here.

- Step 004 (Access application and policy sync) — The destroy command deletes Access applications and their policies. The existing sync functions handle listing and deleting individual Access applications and policies. The destroy command can delegate to these functions or call the SDK directly — the key requirement is that all Access applications listed in the lock file are deleted, along with any that exist in Cloudflare matching the domain pattern but might not be in the lock file (defensive cleanup).

- Step 005 (DNS record sync, redirect rule sync) — The destroy command deletes DNS records and redirect rules. DNS records are identified by listing CNAME records for the zone and filtering for those managed by flaregun (wildcard, per-service, and www records). Redirect rules are identified by finding the bare-domain redirect expression in the `http_request_dynamic_redirect` phase ruleset.

- Step 006 (resource provisioner) — The resource provisioner already has a destruction function that iterates D1/R2/KV entries in the lock file and deletes them via the SDK, with continue-on-failure semantics. The destroy command reuses this function for cloud resource deletion rather than reimplementing the same logic.

- Step 002 (config loader) — The destroy command loads and validates `flaregun.yml` to know the domain name (for the confirmation prompt and for identifying DNS records) and to understand which services existed (for comprehensive cleanup).

## Reuse Opportunities

- **Resource provisioner destruction function from step 006** — The provisioner's destruction function already handles D1/R2/KV deletion with continue-on-failure and lock file cleanup. The destroy command calls this function directly for cloud resource teardown rather than duplicating the logic.

- **Lock file manager from step 003** — The destroy command uses the same load/save/remove/clear operations. After each deletion category succeeds, the relevant entries are removed from the lock state and saved. If all deletions succeed, the lock file is cleared entirely.

- **Environment manager from step 003** — The same validation flow used by `up` and `deploy` applies, except the tunnel token is not required (the destroy command doesn't run the tunnel — it deletes it).

- **SDK client wrapper from step 003** — Same client initialization pattern as all other Cloudflare-interacting commands.

- **Mock client from steps 004/005/006** — The mock client already has tracked methods for Access, DNS, tunnels, D1, R2, KV, and rulesets. The destroy command tests extend the mock with any additional delete methods not yet covered (tunnel deletion, Pages project deletion, Worker deletion).

## Deliverables

### Destroy command handler

The command handler invoked when the user runs `flaregun destroy`.

**Pre-deletion setup (executed in order):**

1. **Load and validate config:** Read `flaregun.yml` via the config loader (step 002). The config is needed for the domain name (used in the confirmation prompt and for identifying DNS records/redirect rules) and for understanding the service layout. If the config is invalid, report the errors and exit — the command cannot proceed without knowing the domain.

2. **Load environment:** Load the `.env` file and validate that the required environment variables are present via the environment manager (step 003). The destroy command requires `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, and `CLOUDFLARE_ZONE_ID`. It does not require `CLOUDFLARE_TUNNEL_TOKEN` — the tunnel token is for running the tunnel, not deleting it. If required variables are missing, report which ones and suggest `flaregun setup`.

3. **Load lock file:** Load `flaregun.lock` via the lock file manager (step 003). If the lock file does not exist or is empty, report that there is nothing to destroy and exit — no Cloudflare resources are tracked.

4. **Initialize SDK client:** Create the Cloudflare SDK client from the loaded credentials.

5. **Confirmation prompt:** Display a warning explaining that this operation will permanently delete all Cloudflare resources managed by flaregun, including data in D1 databases and R2 buckets. List a summary of what will be deleted based on the lock file contents (number of Access applications, tunnel, number of Pages projects, number of D1 databases, number of R2 buckets, number of KV namespaces, fallback Worker, DNS records, redirect rules). Prompt the user to type the domain name exactly to confirm. If the input does not match the domain from the config, abort without deleting anything. If stdin is not a TTY (e.g., piped input), abort with a message that destroy requires interactive confirmation.

### Teardown sequence

After confirmation, execute the deletion steps in order. Each step is independent — a failure in one step does not prevent subsequent steps from executing. Errors are collected and reported in the final summary.

**The ordering is intentional:** Access applications are deleted first because they have policies that reference other resources. The tunnel is deleted early because it routes traffic — once it's gone, subdomains become unreachable. DNS records and redirect rules are deleted next (they reference the tunnel and Pages projects). The fallback Worker is deleted after DNS (it was handling fallback routing). Pages projects are deleted after their custom domains are unlinked (DNS records removed). Cloud resources (D1/R2/KV) are deleted last because Pages projects may reference them via bindings.

### Step 1: Delete Access applications and policies

Delete all Access applications managed by flaregun, along with their associated policies.

**Behavior:**

- Iterate through the `access` section of the lock file, which maps service names to Access application IDs
- For each Access application ID, delete the application via the SDK. Deleting an Access application should also delete its associated policies (the Cloudflare API handles this — deleting the application cascades to its policies)
- If a deletion fails (e.g., application already deleted, permission error), record the error and continue with the remaining applications
- Successfully deleted applications are removed from the lock file's `access` section
- Applications that failed to delete remain in the lock file
- Save the lock file after processing all Access applications

### Step 2: Delete the tunnel

Delete the Cloudflare Tunnel managed by flaregun.

**Behavior:**

- Read the tunnel ID from the lock file's `tunnel` section
- If no tunnel ID is present in the lock file, skip this step
- Delete the tunnel via the SDK using the tunnel ID and account ID. This deletes both the tunnel configuration (ingress rules) and the tunnel itself
- Before deleting the tunnel, the tunnel's connections must be cleaned up. If the tunnel is currently active (has active connections), the delete call may need to force-close connections. Use the appropriate SDK parameter to force deletion even if connections exist.
- If deletion succeeds, remove the tunnel entry from the lock file and save
- If deletion fails, record the error and leave the tunnel entry in the lock file

### Step 3: Delete DNS records

Delete all DNS records managed by flaregun.

**Behavior:**

- List all DNS records in the zone via the SDK using the zone ID
- Identify records managed by flaregun:
  - The wildcard CNAME record (`*.domain`)
  - Per-Pages-service CNAME records (`subdomain.domain` pointing to `*.pages.dev`)
  - The www CNAME record (`www.domain`)
- For each identified record, delete it via the SDK using the zone ID and record ID
- If a deletion fails, record the error and continue with remaining records
- DNS records are not tracked in the lock file (they are identified by listing and filtering), so no lock file update is needed for this step

### Step 4: Delete redirect rules

Remove the flaregun-managed bare-domain redirect rule from the zone's ruleset.

**Behavior:**

- Read the existing `http_request_dynamic_redirect` phase ruleset via the SDK. If the phase doesn't exist, skip this step (nothing to delete)
- Find the rule with the redirect expression matching the domain (`(http.host eq "domain")`)
- If no matching rule is found, skip this step
- Build the updated rules array excluding the flaregun-managed rule (preserve all other rules in the ruleset)
- Push the updated rules via the SDK. If the flaregun rule was the only rule, the ruleset becomes empty
- If the update fails, record the error

### Step 5: Delete the fallback Worker

Delete the domain-specific fallback Worker.

**Behavior:**

- Read the fallback Worker name from the lock file's `worker` section
- If no Worker name is present in the lock file, skip this step
- Delete the Worker script via the SDK using the Worker name
- If deletion succeeds, remove the Worker entry from the lock file and save
- If deletion fails, record the error and leave the Worker entry in the lock file

### Step 6: Delete Pages projects

Delete all Cloudflare Pages projects managed by flaregun.

**Behavior:**

- Iterate through the `pages` section of the lock file, which maps service names to their Pages project data (including `project_name`)
- For each Pages project name, delete the project via the SDK using the account ID and project name. Deleting a Pages project removes all deployments, preview deployments, and custom domain associations for that project
- If a deletion fails (e.g., project not found, permission error), record the error and continue with the remaining projects
- For successfully deleted projects: remove only the `project_name` from the lock file entry, leaving D1/R2/KV resource IDs intact. Step 7 uses the remaining resource IDs to delete cloud resources. After step 7 completes, entries with no remaining fields are removed entirely.
- Save the lock file after processing all Pages projects

### Step 7: Delete cloud resources (D1, R2, KV)

Delete all D1 databases, R2 buckets, and KV namespaces managed by flaregun.

**Behavior:**

- Delegate to the resource provisioner's destruction function from step 006. This function already implements the correct behavior: iterate all resource entries in the lock file, delete each via the SDK, continue on individual failures, remove successfully deleted entries from the lock file, and return a summary
- The destruction function handles D1 databases (by ID), R2 buckets (by name), and KV namespaces (by ID)
- After the destruction function completes, save the lock file

### Step 8: Final lock file cleanup

Clean up the lock file after all deletion steps.

**Behavior:**

- If all resources in all categories were successfully deleted (no errors in any step), clear the lock file entirely — write an empty lock file (or delete the file)
- If some resources failed to delete, the lock file still contains the entries for failed resources. Do not clear it — the user can inspect the lock file to see what remains and re-run `destroy` to retry
- The `.env` file and `flaregun.yml` are NOT deleted by the destroy command. These are user-managed configuration files, not Cloudflare resources. The user keeps them in case they want to re-run `setup` or redeploy later

### Completion summary

After all teardown steps, print a summary of what was accomplished.

**Behavior:**

- Group results by category (Access, tunnel, DNS, redirects, Worker, Pages, D1, R2, KV)
- For each category, report:
  - How many resources were successfully deleted
  - How many failed, with the error message for each failure
- If all resources were deleted successfully, print a success message indicating that all Cloudflare resources have been removed
- If some resources failed to delete, print a warning indicating that the lock file retains entries for failed resources and the user can re-run `flaregun destroy` to retry
- Suggest that the `.env` and `flaregun.yml` files remain and can be removed manually if no longer needed
- Exit with code 0 if all deletions succeeded, or a non-zero exit code if any deletion failed

### Dependency injection for testability

The destroy command accepts all subsystem dependencies as injectable parameters, following the same pattern used by the sync engine, deploy pipeline, and orchestrator.

**Injected dependencies:**

- Config loader function
- Environment manager
- Lock file manager
- SDK client factory
- Resource provisioner destruction function
- Confirmation prompt function (for testing — the default reads from stdin, tests provide a mock that returns a predetermined answer)

**Default implementations** use the real subsystems. Tests provide mock implementations.

### Tests

Tests use the mock Cloudflare SDK client and mock dependencies to verify teardown logic without real API calls. Each test category verifies that the correct SDK methods are called with the correct arguments and that lock file state is updated appropriately.

**Confirmation tests:**
- Typing the correct domain name proceeds with teardown
- Typing an incorrect domain name aborts without any deletions
- An empty input aborts without any deletions
- The confirmation prompt displays a summary of resources to be deleted (counts from lock file)

**Access application deletion tests:**
- Each Access application ID in the lock file results in a delete call via the SDK
- Successfully deleted applications are removed from the lock file's access section
- A failed deletion leaves the entry in the lock file and records the error
- An empty access section in the lock file skips this step (no delete calls)

**Tunnel deletion tests:**
- The tunnel ID from the lock file is used to delete the tunnel via the SDK
- A successful tunnel deletion removes the tunnel entry from the lock file
- A failed tunnel deletion leaves the entry in the lock file and records the error
- A missing tunnel ID in the lock file skips this step

**DNS record deletion tests:**
- The wildcard CNAME record is identified and deleted
- Per-Pages-service CNAME records are identified and deleted
- The www CNAME record is identified and deleted
- DNS records not managed by flaregun (e.g., MX records, TXT records, user-created CNAMEs) are not deleted
- A failed DNS record deletion records the error and continues with remaining records

**Redirect rule deletion tests:**
- The flaregun-managed redirect rule is identified by its expression and removed from the ruleset
- Other rules in the same phase ruleset are preserved
- If no matching redirect rule exists, the step is skipped
- If the phase ruleset does not exist, the step is skipped

**Worker deletion tests:**
- The Worker name from the lock file is used to delete the Worker via the SDK
- A successful deletion removes the Worker entry from the lock file
- A failed deletion leaves the entry in the lock file and records the error
- A missing Worker name in the lock file skips this step

**Pages project deletion tests:**
- Each Pages project name in the lock file results in a delete call via the SDK
- Successfully deleted projects have their project name removed from the lock file
- A failed deletion leaves the entry in the lock file and records the error
- An empty pages section in the lock file skips this step

**Cloud resource deletion tests:**
- The resource provisioner's destruction function is called
- D1 databases, R2 buckets, and KV namespaces from the lock file are all deleted
- Successfully deleted resources are removed from the lock file
- Failed deletions remain in the lock file (delegated to the provisioner's continue-on-failure behavior)

**Lock file cleanup tests:**
- If all deletions succeed, the lock file is cleared entirely
- If some deletions fail, the lock file retains only the failed entries
- The lock file is saved after each deletion category (not just once at the end) so that progress is preserved if the command is interrupted

**Continue-on-failure tests:**
- A failure in Access application deletion does not prevent tunnel deletion
- A failure in tunnel deletion does not prevent DNS record deletion
- A failure in DNS record deletion does not prevent subsequent steps
- All errors are collected and reported in the final summary
- The exit code is non-zero when any deletion failed

**Pre-deletion validation tests:**
- An invalid config aborts before the confirmation prompt
- Missing environment variables abort before the confirmation prompt
- An empty or missing lock file exits with a message that there is nothing to destroy
- The destroy command does not require the tunnel token (only API token, account ID, zone ID)

**Summary output tests:**
- A fully successful destroy reports all categories as deleted and exits with code 0
- A partially successful destroy reports successes and failures by category and exits with non-zero
- The summary suggests manual removal of `.env` and `flaregun.yml`
