# 001: Project setup, CLI skeleton, and process utilities

## Context

This is the foundational step for the entire flaregun project. Nothing exists yet — the repo is empty aside from a README, .gitignore, and the tasks/ directory. This step establishes the Bun project structure, installs all dependencies, configures TypeScript, creates the CLI entry point with its command dispatcher, and ports the process utility functions from the personal-homepage project. Every subsequent step depends on this foundation.

## Related Code

Existing files/patterns to reference or extend:

- `../personal-homepage/package.json` — Reference for the Bun project structure, `"type": "module"`, and the `"test": "bun test"` script. Flaregun uses the same runtime and testing approach but adds more dependencies (React, Zustand, MUI will come later — only install what's needed now).
- `../personal-homepage/tsconfig.json` — Reference for TypeScript configuration targeting ESNext with Bun module resolution, strict mode, and `"types": ["bun"]`. Flaregun should follow the same pattern but scope `include` to `src/` and `tests/`.
- `../personal-homepage/scripts/lib/process.ts` — Contains `binaryExists()` and `runCommand()` with the `CommandRunner` type for dependency injection. These utilities transfer directly to flaregun with minimal changes. The `CommandResult` interface and injectable `CommandRunner` type are the key patterns.
- `../personal-homepage/Makefile` — Reference for how commands are invoked (e.g., `bun run scripts/up.ts`). Flaregun replaces this with a proper CLI entry point.

## Reuse Opportunities

- **Process utilities** (`binaryExists`, `runCommand`, `CommandRunner` type) from `../personal-homepage/scripts/lib/process.ts` can be ported directly. The implementation uses `Bun.spawn()` for process execution and `which` for binary detection — keep this approach. The `CommandRunner` type is important because later steps (sync engine, deploy pipeline) use it for dependency injection in tests.
- **TypeScript configuration** from the personal-homepage project can be adapted with minor changes to the include/exclude paths.
- **Package structure** follows the same Bun-native pattern: `"type": "module"`, no bundler for the CLI itself, `bun test` for the test runner.

## Deliverables

### Project initialization

- A `package.json` for the flaregun project with the project name, version, module type, and dependencies needed for this step and the near future: `cloudflare` (Cloudflare SDK), `js-yaml` (YAML parsing), and their type definitions. Also include `@cloudflare/workers-types` as a dev dependency (needed later for functions scaffolding). The test script should use `bun test`.
- A `tsconfig.json` targeting ESNext with Bun module resolution, strict mode enabled, and Bun types included. The include paths should cover `src/` and `tests/` directories.
- A `.gitignore` that covers `node_modules/`, `dist/`, `.env`, and any build artifacts. The lock file `flaregun.lock` should NOT be gitignored (it's meant to be committed).
- Run `bun install` to generate `bun.lockb`.

### Directory structure

Create the initial directory structure:

- `src/` — All CLI source code
- `src/cli/` — CLI entry point and command dispatcher
- `src/process/` — Process utilities (binaryExists, runCommand)
- `tests/` — Test files

### CLI entry point and command dispatcher

- A main entry point file in `src/cli/` that reads `process.argv` to determine which command to run.
- The dispatcher recognizes the commands: `up`, `down`, `deploy`, `build`, `setup`, `destroy`.
- The `build` and `deploy` commands accept optional trailing arguments as service name filters (e.g., `flaregun build homepage blog` passes `["homepage", "blog"]` to the handler).
- Running with `--help` or `-h` flag, or with no arguments, displays help text listing all available commands with brief descriptions.
- Running with an unrecognized command displays an error message and the help text, then exits with a non-zero code.
- Each command has a placeholder handler that prints a "not yet implemented" message and exits — the actual command implementations come in later steps.
- The entry point should be runnable via `bun run src/cli/index.ts` or equivalent.

### Process utilities

- Port `binaryExists()` from the personal-homepage project into `src/process/`. It checks whether a named binary is available on the system PATH by attempting to run `which`. Returns a boolean.
- Port `runCommand()` into `src/process/`. It spawns a child process with the given arguments and working directory, captures stdout and stderr, waits for completion, and returns the exit code along with the captured output.
- Port the `CommandResult` type (exit code, stdout, stderr) and the `CommandRunner` function type for dependency injection in tests.

### Tests

- Tests for the CLI dispatcher: verify that each recognized command name dispatches to its handler, that `--help` and no-argument invocations produce help text, and that unknown commands produce an error with help text.
- Tests for `binaryExists`: verify it returns true for a binary known to exist (e.g., `bun`), and false for a nonexistent binary name.
- Tests for `runCommand`: verify it returns exit code 0 and captured stdout for a successful command, returns a non-zero exit code and captured stderr for a failing command, and respects the working directory argument.
