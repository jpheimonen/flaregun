# 013: Hot-reload engine

## Context

The hot-reload engine makes config changes take effect without restarting `flaregun up`. When a user edits `flaregun.yml` via the admin UI and clicks save, the admin backend (step 012) writes the new config to disk and hands the old and new parsed configs to the hot-reload engine. The engine computes the diff (using the config differ from step 002), categorizes each change, and applies the appropriate actions — starting/stopping services, updating Access policies, refreshing tunnel ingress — without interrupting unaffected services.

This is entirely new functionality. The personal-homepage project has no hot-reload capability — changes require restarting the `up` script. Flaregun's engine is built on top of existing components: the config differ (step 002) provides the structured diff, the process supervisor (step 011) handles service lifecycle changes, and the individual sync functions from steps 004/005 handle Cloudflare state mutations. The hot-reload engine is the orchestrator that maps diff categories to the correct actions.

The engine must be resilient. A failure in one action (e.g., Cloudflare API error while creating an Access application) must not crash the running system or prevent other actions from being applied. The engine collects errors and returns them so the admin UI can report which changes succeeded and which failed. The config is already saved to disk at this point — the user can retry or run `flaregun up` for a full re-sync.

## Related Code

Existing files/patterns to reference or extend:

- Step 002 (config differ) — The differ produces a structured diff with added/removed/modified services and global auth changes. Modified services carry per-field change categorization (runtime-affecting vs. Pages-only). The hot-reload engine consumes this diff and maps each category to actions.

- Step 004 (Access application and policy sync) — The individual sync functions (`syncAccessApplications`, `syncAccessPolicies`) are called by the hot-reload engine when auth-related changes are detected. The engine does not reimplement Access logic — it delegates to the existing sync functions.

- Step 005 (tunnel ingress sync) — The `syncTunnelIngress` function is called by the hot-reload engine when services are added, removed, or have their ports changed. Since ingress sync is a full replacement operation (rebuilds the entire ingress array from the current config), it naturally handles additions and removals.

- Step 011 (process supervisor) — The supervisor's API is called by the hot-reload engine: `start()` for added services, `stop()` for removed services, `restart()` for services with command or port changes.

- Step 003 (lock file manager) — The engine saves the lock file after any Cloudflare resource mutations (Access apps created/deleted, etc.).

- Step 003 (SDK client) — The engine needs the Cloudflare SDK client for Access and ingress sync operations. The client is provided by the orchestrator at `flaregun up` startup and passed through the admin backend to the hot-reload engine.

## Reuse Opportunities

- **Sync functions from steps 004/005** — The hot-reload engine does not reimplement any Cloudflare sync logic. It calls the same `syncAccessApplications`, `syncAccessPolicies`, and `syncTunnelIngress` functions that the full sync orchestrator uses. This ensures consistency — the same logic that runs during `flaregun up`'s initial sync also runs during hot-reload.

- **Config differ from step 002** — The differ already categorizes changes into exactly the categories the engine needs. The engine's job is mapping categories to actions, not computing the diff.

- **Process supervisor API from step 011** — All service lifecycle changes go through the supervisor's programmatic interface. The engine does not spawn or kill processes directly.

- **Lock file manager from step 003** — The engine uses the same save mechanism to persist Cloudflare resource changes.

## Deliverables

### Hot-reload engine

A function that accepts the old and new parsed configs plus the runtime dependencies (process supervisor, Cloudflare SDK client, lock file state, environment credentials) and applies all necessary changes.

**Behavior:**

- Compute the diff between old and new configs using the config differ from step 002
- If the diff is empty (configs are identical), return immediately with no actions taken
- Process each change category and apply the corresponding actions (detailed below)
- Collect errors from each action without aborting — continue processing remaining changes even if one fails
- After all actions are applied, save the lock file if any Cloudflare resources were modified
- Return a result object listing which actions were taken and which errors occurred

### Change category: Service added

When a new service appears in the config (present in new, absent in old):

**Local service added:**
- Start the service via the process supervisor
- If the service has non-public auth (`admin_only` or `authorized`), create an Access application and policy for its subdomain via the Access sync functions
- Update tunnel ingress rules to include the new subdomain (call `syncTunnelIngress` with the new config)

**Pages service added:**
- If the service has non-public auth, create an Access application and policy for its subdomain
- No process to start (Pages services are not supervised)
- No ingress rule needed (Pages services are served by Cloudflare Pages, not the tunnel)
- The rest (provisioning, deploying) happens at the next `flaregun deploy` — no runtime action

### Change category: Service removed

When a service disappears from the config (present in old, absent in new):

**Local service removed:**
- Stop the service via the process supervisor
- If the service had an Access application (non-public auth), delete it and its policy via the Access sync functions. Remove the Access application entry from the lock file.
- Update tunnel ingress rules to exclude the removed subdomain (call `syncTunnelIngress` with the new config — since ingress is a full replacement, the removed service is automatically absent)

**Pages service removed:**
- If the service had an Access application, delete it and its policy. Remove the entry from the lock file.
- No process to stop
- The actual Pages project remains in Cloudflare until `flaregun destroy` — hot-reload does not delete deployed infrastructure

### Change category: Service modified — runtime-affecting fields

When a service exists in both configs but has changes to fields that affect the running system:

**Port changed (local service):**
- Restart the service via the process supervisor (the new command or same command will use the new port)
- Update tunnel ingress rules (call `syncTunnelIngress` with the new config)

**Command changed (local service):**
- Restart the service via the process supervisor with the new command

**Auth mode changed:**
- If changed from `public` to `admin_only` or `authorized`: create an Access application and policy for the subdomain
- If changed from `admin_only` or `authorized` to `public`: delete the Access application and policy. Remove the entry from the lock file.
- If changed between `admin_only` and `authorized` (both non-public): update the Access policy selectors to reflect the new user list. If changing to `admin_only`, the policy becomes superusers-only. If changing to `authorized`, the policy adds per-service users.

**Users list changed (on an `authorized` service):**
- Update the Access policy with the new selector list via the policy sync function

**max_retries changed (local service):**
- Update the supervisor's configuration for that service. No restart needed — the new limit takes effect on the next crash.

### Change category: Global auth changes

When the top-level auth config changes (superusers list or identity provider):

**Superusers changed:**
- Update all Access policies for all non-public services, since superusers are included in every policy. Call the policy sync function for each affected application.

**Identity provider changed:**
- This is a portal-level configuration — flaregun does not manage identity provider settings programmatically. Log a note that the identity provider setting has changed in the config but that the user must update the Cloudflare Access configuration in the portal manually.

### Change category: Pages-only fields

When only Pages-specific fields change on a service (`dist`, `build`, `functions`, `database`, `bucket`, `kv`):

- Take no runtime action. These changes only affect the next `flaregun deploy` or `flaregun build`.
- The engine should recognize these as Pages-only changes and explicitly skip them (not treat them as unknown changes).

### Change category: Domain changed

If the domain field itself changes:

- This is a major configuration change that affects every resource. The hot-reload engine should not attempt to handle this — it should return an error indicating that the domain cannot be changed via hot-reload. The user should stop `flaregun up`, update the config, and restart to do a full re-sync.

### Error handling and resilience

The hot-reload engine must never crash the running system.

**Behavior:**

- Each action (start service, create Access app, update ingress, etc.) is wrapped in error handling
- If an action fails, record the error (what was attempted, what went wrong) and continue with the remaining actions
- The result object contains both successful actions and failed actions with their error details
- The admin UI backend (step 012) returns this result to the frontend, which can display what succeeded and what failed
- Even if all actions fail, the system continues running with whatever state it had before the reload
- The new config has already been written to disk by the admin backend before the engine runs. If the engine partially fails, the on-disk config and the running state may diverge. Running `flaregun up` performs a full re-sync to resolve this.

### Tests

Tests use mock/stub implementations of the process supervisor, sync functions, and lock file manager. The tests verify that the engine maps diff categories to the correct actions without actually starting processes or calling Cloudflare APIs.

**Service addition tests:**
- Adding a local service to the config starts that service via the process supervisor
- Adding a local service with non-public auth creates an Access application and policy
- Adding a local service updates the tunnel ingress rules
- Adding a Pages service with non-public auth creates an Access application and policy
- Adding a Pages service does not start any process or update ingress rules

**Service removal tests:**
- Removing a local service stops it via the process supervisor
- Removing a service with an Access application deletes the application and policy
- Removing a local service updates the tunnel ingress rules
- Removing a Pages service does not stop any process

**Service modification tests:**
- Changing a service's port restarts the service and updates ingress rules
- Changing a service's command restarts the service with the new command
- Changing a service's auth from `public` to `authorized` creates an Access application and policy
- Changing a service's auth from `authorized` to `public` deletes the Access application and policy
- Changing a service's auth between `admin_only` and `authorized` updates the Access policy selectors
- Changing the users list on an `authorized` service updates the Access policy
- Changing `max_retries` updates the supervisor configuration without restarting

**Global auth change tests:**
- Changing the global superusers list updates all non-public Access policies
- Changing the identity provider logs a note but takes no programmatic action

**Pages-only change tests:**
- Changes to `dist`, `build`, `functions`, `database`, `bucket`, `kv` do not trigger any runtime actions
- A service with both runtime changes and Pages-only changes applies only the runtime actions

**Domain change test:**
- Changing the domain field returns an error indicating domain changes require a full restart

**No-op test:**
- Identical configs produce no actions (empty diff → immediate return)

**Error handling tests:**
- A failure in one action (e.g., Access app creation fails) does not prevent other actions from being applied
- The result includes both successful and failed actions
- The lock file is saved after successful Cloudflare mutations even if other actions failed
- A hot-reload failure does not crash or stop the running system

**Lock file tests:**
- The lock file is saved after any Cloudflare resources are modified (Access apps created/deleted)
- The lock file is not saved if no Cloudflare resources were modified (e.g., only local service restarts)
