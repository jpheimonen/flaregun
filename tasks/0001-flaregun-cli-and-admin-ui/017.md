# 017: Setup wizard

## Context

The setup wizard (`flaregun setup`) provides a guided interactive walkthrough for first-time Cloudflare configuration. Setting up flaregun from scratch requires navigating several Cloudflare portal pages, creating API tokens with specific permissions, configuring an identity provider for Access, and creating a tunnel — a process that is confusing and error-prone for anyone unfamiliar with Cloudflare's product surface. The wizard reduces this to a step-by-step guided flow.

The setup wizard is the only command that operates without an existing `flaregun.yml` or `.env` file — it creates them. All other commands require these files to exist. The wizard is designed to be run once during initial project setup, though it can be re-run to regenerate files if needed (with overwrite confirmation).

The personal-homepage project has no setup wizard — it relies on manual `.env` creation using `.env.example` as a reference. Flaregun replaces this with an automated guided flow that validates credentials as they are entered and creates the tunnel programmatically.

## Related Code

Existing files/patterns to reference or extend:

- `../personal-homepage/.env.example` — Documents the five environment variables the existing project needs. Flaregun's setup wizard generates a `.env` with four variables: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_ZONE_ID`, and `CLOUDFLARE_TUNNEL_TOKEN`. The tunnel ID is stored in the lock file instead of the env file (since it's not a secret).

- Step 003 (SDK client wrapper) — The wizard creates a temporary Cloudflare SDK client using the token the user provides, then uses it to verify the token and create the tunnel. This follows the same client initialization pattern as the regular SDK client wrapper.

- Step 003 (lock file manager) — After creating the tunnel, the wizard stores the tunnel ID in the lock file. This is the first write to `flaregun.lock` for a new project.

- Step 003 (environment manager) — The wizard generates the `.env` file with the same variable names that the environment manager expects. After setup, `flaregun up` and `flaregun deploy` should work without additional env configuration.

- Step 002 (config loader) — The wizard generates a starter `flaregun.yml` that must pass the config loader's validation. The starter config should be a valid, minimal config.

## Reuse Opportunities

- **SDK client from step 003** — The wizard creates a Cloudflare SDK client to verify the token and create the tunnel. It uses the same client wrapper but with credentials provided interactively rather than loaded from `.env`.

- **Lock file manager from step 003** — The wizard stores the tunnel ID in the lock file using the same manager that the sync engine and provisioner use.

- **Config validation from step 002** — The generated starter config should pass `parseConfig()` validation. The wizard can optionally validate its generated config as a sanity check.

## Deliverables

### Setup wizard command handler

The command handler invoked when the user runs `flaregun setup`. Walks the user through five steps sequentially, prompting for input at each stage.

**Overall behavior:**

- The wizard is interactive — it reads user input from stdin and writes prompts/instructions to stdout
- Each step depends on the output of previous steps (e.g., the token from step 1 is used in step 3 to create the tunnel)
- If a step fails (e.g., token validation), the wizard re-prompts rather than aborting entirely
- At the end, the wizard prints a summary of what was created and suggests running `flaregun up` next

### Step 1: API token

Guide the user through creating a Cloudflare API token with the correct permissions.

**Behavior:**

- Display clear instructions explaining what an API token is and why it's needed
- List the exact permissions the token needs:
  - Account: Cloudflare Tunnel: Edit
  - Account: Access: Organizations, Identity Providers, and Groups: Edit
  - Account: Access: Apps and Policies: Edit
  - Account: D1: Edit
  - Account: Workers R2 Storage: Edit
  - Account: Workers KV Storage: Edit
  - Zone: DNS: Edit
  - Zone: Zone Rulesets: Edit
  - Zone: Cloudflare Pages: Edit
  - Zone: Workers Routes: Edit
- Provide a direct URL to the Cloudflare dashboard's token creation page
- Prompt the user to paste the token
- **Validate the token** by making a test API call (the token verify endpoint via the SDK). If validation succeeds, confirm success and show the token status. If validation fails, display a descriptive error and re-prompt.
- After successful validation, also prompt for or automatically determine the account ID and zone ID:
  - **Account ID:** Prompt the user to enter it (with instructions on where to find it in the Cloudflare dashboard), or attempt to list accounts using the token and let the user select if multiple exist
  - **Zone ID:** Prompt the user for their domain name, then look up the zone ID via the SDK using the domain name. If the zone is not found, display an error and re-prompt.

### Step 2: Identity provider

Guide the user through configuring an identity provider in Cloudflare Access.

**Behavior:**

- Display instructions explaining that Cloudflare Access needs an identity provider for authentication (this is how users log in to access protected services)
- List common providers (Google OAuth, GitHub, etc.) with brief descriptions
- Provide a direct URL to the Cloudflare Access identity provider configuration page
- Explain the required portal steps (this cannot be automated — the user must configure the provider in the Cloudflare dashboard)
- Prompt for the identity provider name that the user configured (e.g., "google", "github"). This is stored in `flaregun.yml` as the `provider` field in the auth section.
- Also prompt for the user's email address (or multiple emails) to use as superusers. These are the admin emails that get access to all protected services.

### Step 3: Tunnel creation

Programmatically create a Cloudflare Tunnel via the SDK.

**Behavior:**

- Use the validated API token and account ID from step 1 to create a new tunnel via the Cloudflare SDK
- Derive a tunnel name from the domain (e.g., `example-com-tunnel`)
- The SDK response includes both the tunnel ID and the tunnel token
- Store the tunnel ID for the lock file
- Store the tunnel token for the `.env` file
- Display a success message with the tunnel name and ID
- If tunnel creation fails (e.g., a tunnel with the same name already exists), display the error and offer to either use the existing tunnel or choose a different name

### Step 4: Generate `.env` file

Write the `.env` file with all collected credentials.

**Behavior:**

- Assemble the environment variables collected from steps 1 and 3:
  - `CLOUDFLARE_API_TOKEN` — from step 1
  - `CLOUDFLARE_ACCOUNT_ID` — from step 1
  - `CLOUDFLARE_ZONE_ID` — from step 1 (looked up from the domain)
  - `CLOUDFLARE_TUNNEL_TOKEN` — from step 3 (tunnel creation response)
- **Overwrite protection:** If a `.env` file already exists, prompt the user for confirmation before overwriting. If the user declines, skip this step and continue.
- Write the file with descriptive comments explaining each variable (similar to the existing `.env.example` format)
- Remind the user that this file should be gitignored (it contains secrets)

### Step 5: Generate starter `flaregun.yml`

Generate a minimal but valid config file.

**Behavior:**

- Generate a `flaregun.yml` containing:
  - **domain:** The domain name entered/confirmed in step 1
  - **auth section:** The identity provider name and superuser email(s) from step 2
  - **One example homepage service:** A Pages service with a `dist` path pointing to a sensible default (e.g., `projects/homepage/dist`), providing a starting point the user can customize
- The generated config must pass the config loader's validation (step 002)
- Include YAML comments explaining each field and suggesting next steps (e.g., "Add more services here", "Change auth to 'public' for open services")
- **Overwrite protection:** If a `flaregun.yml` already exists, prompt the user for confirmation before overwriting. If the user declines, skip this step and continue.

### Step 6: Initialize lock file

Write the initial `flaregun.lock` with the tunnel ID.

**Behavior:**

- Store the tunnel ID from step 3 in the lock file via the lock file manager (step 003)
- If a lock file already exists (re-running setup), merge the tunnel ID into the existing lock file rather than overwriting it

### Completion summary

After all steps, print a summary of what was accomplished and next steps.

**Behavior:**

- List what was created/configured:
  - API token validated
  - Identity provider configured (manual step)
  - Tunnel created with name and ID
  - `.env` file generated (or skipped if declined)
  - `flaregun.yml` generated (or skipped if declined)
  - Lock file initialized with tunnel ID
- Suggest next steps:
  - Edit `flaregun.yml` to add your services
  - Run `flaregun up` to start the system
  - Run `flaregun deploy` to deploy Pages services

### Tests

The setup wizard is interactive, which makes unit testing individual steps easier than testing the full flow. Tests mock stdin for user input and mock the Cloudflare SDK for API calls.

**Token validation tests:**
- A valid API token passes validation (mock SDK returns success from the verify endpoint)
- An invalid API token fails validation with a descriptive error
- After a failed validation, the wizard re-prompts (mock provides valid token on second call)

**Account and zone lookup tests:**
- A valid domain name resolves to a zone ID via the SDK
- An invalid domain name produces an error and re-prompts

**Tunnel creation tests:**
- A tunnel is created programmatically via the SDK with the correct name and account ID
- The tunnel ID and token are extracted from the SDK response
- If tunnel creation fails (e.g., name conflict), an error is shown

**File generation tests:**
- The generated `.env` file contains all four required environment variables with the correct values
- The generated `.env` file includes descriptive comments
- The generated `flaregun.yml` contains the user's domain, auth provider, superusers, and a homepage service
- The generated `flaregun.yml` passes config loader validation
- The generated `flaregun.yml` includes helpful comments

**Overwrite protection tests:**
- If `.env` does not exist, it is written without prompting
- If `.env` already exists, the user is prompted for confirmation before overwriting
- If the user declines to overwrite `.env`, the file is left unchanged
- If `flaregun.yml` does not exist, it is written without prompting
- If `flaregun.yml` already exists, the user is prompted for confirmation before overwriting
- If the user declines to overwrite `flaregun.yml`, the file is left unchanged

**Lock file tests:**
- The tunnel ID is stored in the lock file after tunnel creation
- If a lock file already exists, the tunnel ID is merged without overwriting other entries
