# 004: Sync engine: Access applications and policies

## Context

The sync engine is the heart of flaregun's Cloudflare state management — it ensures the live Cloudflare configuration matches the declared `flaregun.yml`. This step implements the first two sync steps: Access applications and Access policies. These are closely coupled (policies belong to applications) and must be built together.

The personal-homepage project has well-tested implementations of both steps, but they only handle creation and updates — they never delete stale resources. Flaregun must handle removals: when a service is deleted from config or changes from non-public to public auth, its Access application and policy must be cleaned up. Additionally, flaregun has an implicit `admin` subdomain that always gets an Access application with admin_only auth, even though it's not in the user's config.

This step also establishes the mock Cloudflare SDK test pattern (`createMockClient()`) that will be reused by steps 005, 006, and 009.

## Related Code

Existing files/patterns to reference or extend:

- `../personal-homepage/scripts/sync.ts` (lines 77–211) — `syncAccessApplications()` and `syncAccessPolicies()` implement the exact logic being adapted. Applications: list existing via paginated async iterable, match by hostname, create if missing, skip if present. Policies: list existing per-app, match by name, create if missing, update if selectors changed (using JSON.stringify comparison). Both accept the Cloudflare SDK client, config, and account ID as parameters.

- `../personal-homepage/scripts/sync.test.ts` (lines 58–236) — `createMockClient()` factory builds a mock with call tracking (`track()` helper), in-memory state stores (apps array, policies record keyed by app ID), and state manipulation methods (`setApps`, `getApps`, `setPolicies`, etc.). `mockPageResult()` simulates the SDK's async iterable pagination. Test step functions (`syncAppsStep`, `syncPoliciesStep`) mirror the production code but accept the mock client.

- `../personal-homepage/scripts/sync.test.ts` (lines 520–790) — Test cases for Access application idempotency (first sync creates, second sync skips, adding a service creates only the new one, services with `auth: none` are skipped) and Access policy construction (superuser-only selectors, combined selectors with per-service users, wildcard domain selectors, policy update on user list change, idempotency of policy sync).

- `../personal-homepage/scripts/lib/config.ts` (lines 267–291) — `buildServiceSelectors()` and supporting functions (`mergeUsers`, `toAccessSelectors`) are used by the policy sync step to construct the correct selector lists. In flaregun, these live in the config module (step 002) with adapted auth modes.

## Reuse Opportunities

- **Application sync logic** — The list-then-match-then-create pattern from `syncAccessApplications()` transfers directly. The key adaptation is adding deletion logic for removed services, adding the implicit admin subdomain application, and using the new three-tier auth model (`admin_only`/`authorized` → create app; `public` → skip/delete).

- **Policy sync logic** — The `syncAccessPolicies()` pattern of listing existing policies per-app, matching by name, creating if missing, and updating if selectors differ (via JSON comparison) transfers directly. Adapt `buildServiceSelectors()` for the new auth model.

- **Mock client factory** — The `createMockClient()` pattern is the foundation for all sync engine tests. Flaregun's version should be extended to include `delete` methods on applications and policies (the existing mock doesn't have them because the existing sync never deletes). The mock should also add the D1/R2/KV and tunnel-related methods that later steps will need — or at minimum be designed to be extended incrementally.

- **Test fixture helper** — The `makeConfig()` helper that creates a valid config object with overridable fields should be adapted for flaregun's config shape (Pages services, local services, three-tier auth, etc.).

- **Pagination helper** — The `collectPages()` async iterable collector and `mockPageResult()` test helper transfer directly.

## Deliverables

### Sync engine module structure

Create `src/sync/` with separate files for each sync step. This step creates the Access application and policy sync functions. The functions follow the dependency injection pattern: they accept the Cloudflare SDK client, the parsed config, credentials (account ID), and the lock file state as parameters — they do not create their own client or load config.

### Access application sync

A function that ensures Cloudflare Access self-hosted applications exist for every service that requires auth protection.

**Behavior:**

- List all existing Access applications in the account via the paginated SDK API
- For each service in the config with `admin_only` or `authorized` auth:
  - Construct the hostname as `subdomain.domain`
  - Check if an application already exists for that hostname
  - If it exists, skip creation (idempotent). Store the application ID in the lock file state.
  - If it does not exist, create a new self-hosted Access application. Store the new application ID in the lock file state.
- **Implicit admin service:** Always ensure an Access application exists for `admin.domain` with admin_only auth, even though the admin service is not in the user's config. This application protects the admin UI.
- **Removal handling:** Compare the set of services in the current config against the services tracked in the lock file. For any service that exists in the lock file but is no longer in the config (or has changed to `public` auth), delete its Access application via the SDK and remove its entry from the lock file.
- Return the list of managed applications (ID, name, hostname) for use by the policy sync step.

### Access policy sync

A function that ensures each Access application has a policy with the correct set of allowed users.

**Behavior:**

- For each managed application (from the application sync output):
  - Determine the correct selectors using `buildServiceSelectors()` from the config module. For `admin_only` services, this is superusers only. For `authorized` services, this is superusers merged with per-service users. The implicit admin service uses superusers only.
  - List existing policies for this application via the paginated SDK API
  - If no policy exists, create one with the computed selectors
  - If a policy exists but its selectors differ from the computed set (detected via deep comparison), update the policy with the new selectors
  - If a policy exists and its selectors match, skip (idempotent)
- Policies for deleted applications are implicitly cleaned up when the application is deleted (Cloudflare cascades policy deletion when an application is removed).

### Mock Cloudflare SDK client

A test utility — `createMockClient()` — that builds a mock Cloudflare SDK client for testing sync logic without real API calls.

**Design:**
- Call tracking: a `track()` mechanism that records every API method call with its arguments, queryable via a `getCalls(methodName)` function
- In-memory state stores for applications (array), policies (record keyed by app ID), and later sync steps' data
- State manipulation methods for test setup: `setApps()`, `getApps()`, `setPolicies()`, `getPolicies()`
- All list methods return `mockPageResult()` async iterables
- Create methods add to the in-memory stores and return realistic response shapes
- **New for flaregun:** Delete methods that remove from the in-memory stores and track the call. The existing personal-homepage mock does not have delete methods because the existing sync never deletes.
- The mock should be designed so that future steps (005, 006) can extend or reuse it for tunnel, DNS, redirect, and resource provisioning operations. Place it in a shared test utilities location.

### Test fixtures

A `makeConfig()` helper adapted for flaregun's config shape. Should produce a valid config with sensible defaults and support overriding specific fields (domain, auth, services). Services should default to the new format (Pages services with `dist`, local services with `command`+`port`, three-tier auth modes).

### Tests

Follow the personal-homepage test organization: `describe` blocks per sync step, each test using the mock client and fixtures.

**Access application tests:**
- First sync with no existing remote applications creates one application per non-public service
- Second sync with identical config makes zero create calls (idempotency)
- Adding a new service to the config creates only that service's application
- A service with `public` auth does not get an Access application
- The `admin` subdomain always gets an Access application (implicit service)
- A service removed from config results in its Access application being deleted via the SDK
- A service that changes from `authorized` to `public` results in its Access application being deleted
- A service that changes from `public` to `authorized` results in a new Access application being created
- Application IDs are stored in the lock file state after creation

**Access policy tests:**
- An `admin_only` service gets a policy with only superuser email selectors
- An `authorized` service gets a policy combining superuser emails with per-service user emails
- Wildcard domain users produce email_domain selectors in the policy
- Exact email users produce email selectors in the policy
- Second sync with identical config makes zero policy create calls (idempotency)
- When the user list changes for a service, the existing policy is updated with new selectors
- Superusers are always included in every non-public policy regardless of the service's own user list
- The implicit admin service gets a policy with only superuser selectors

**Combined access sync tests:**
- A full access sync (applications + policies) for a multi-service config creates the expected applications and policies
- Running the full access sync twice with identical config produces zero create/delete calls on the second run
