# 002: Config loader with validation, type inference, and diffing

## Context

The config loader is the most foundational runtime component — every command except `setup` starts by loading and validating `flaregun.yml`. This step builds the config parsing, validation, type inference, access selector utilities, and config diffing. The personal-homepage project has a well-tested config system that provides the foundation, but flaregun's config model is significantly expanded: services no longer have a fixed shape (they're inferred as Pages or local from their properties), auth modes change from binary required/none to a three-tier model, new fields like `dist`, `build`, `functions`, `database`, `bucket`, `kv`, `max_retries`, and `down_page` are added, and reserved subdomain validation is introduced. Config diffing is entirely new — it's needed by the hot-reload engine (step 013) to apply granular changes when the admin UI saves config updates.

## Related Code

Existing files/patterns to reference or extend:

- `../personal-homepage/scripts/lib/config.ts` — The config loader that flaregun's is adapted from. Key patterns: `parseConfig()` accepts a YAML string (testable without filesystem), `loadConfig()` reads from disk, `validateConfig()` collects all errors eagerly in an array before throwing `ConfigValidationError`. Separate internal functions for service entry validation (`validateServiceEntries`) and typed object construction (`buildTypedServices`). Access selector utilities (`isWildcard`, `extractWildcardDomain`, `mergeUsers`, `toAccessSelectors`, `buildServiceSelectors`) live in the same module.

- `../personal-homepage/scripts/lib/config.test.ts` — Test patterns to follow. Uses an `expectValidationErrors()` helper that calls `parseConfig()` with invalid YAML and returns the error strings. Tests check for specific keywords in error messages (e.g., `msg.includes("domain")`) rather than exact string matching — this is more resilient to message wording changes. Uses YAML template literal constants (e.g., `VALID_YAML`, `MULTI_SERVICE_YAML`) for test fixtures. Organized into `describe` blocks: parsing, validation, user utilities, access selectors.

- `../personal-homepage/config.yaml` — The current config format. Flaregun's format differs: file is named `flaregun.yml`, services no longer require `port`/`command` (Pages services have `dist` instead), auth uses `admin_only`/`authorized`/`public` instead of `required`/`none`, and new fields are added for cloud resources and Pages Functions.

## Reuse Opportunities

- **Eager error collection pattern** — The `validateConfig()` approach of collecting errors in an array and throwing `ConfigValidationError` with all errors at the end transfers directly. The `ConfigValidationError` class with `errors: string[]` is reusable as-is.

- **`parseConfig()` / `loadConfig()` split** — The pattern of separating string-based parsing (testable) from filesystem-based loading (convenience) should be preserved. `parseConfig()` is heavily used in tests.

- **Access selector utilities** — `isWildcard()`, `extractWildcardDomain()`, `mergeUsers()`, `toAccessSelectors()` are reusable as-is. `buildServiceSelectors()` needs adaptation to work with the new three-tier auth model (`admin_only`/`authorized`/`public` instead of `required`/`none`).

- **Duplicate detection logic** — The port and subdomain uniqueness checking via Maps transfers directly, though port uniqueness now only applies to local services (Pages services don't have ports).

- **Test helper pattern** — The `expectValidationErrors()` helper and keyword-matching assertion style from `config.test.ts` should be reused.

## Deliverables

### Config types

Define types representing the parsed flaregun.yml structure:

- A top-level config type containing `domain` (string), `auth` (auth config), optional `down_page` (string path), and `services` (map of service name to service config).
- An auth config type containing `provider` (string) and `superusers` (string array).
- A service config type that includes all possible fields: `subdomain`, `auth` (defaulting to `admin_only`), `users` (optional string array), `dist` (optional string), `build` (optional string), `functions` (optional string), `database` (optional boolean), `bucket` (optional boolean), `kv` (optional boolean), `command` (optional string), `port` (optional number), `max_retries` (optional number).
- Each parsed service config should carry an internally-set classification indicating whether it is a Pages service or a local service. This classification is determined by the loader, not set by the user.

### Config loading and parsing

- A `loadConfig()` function that reads `flaregun.yml` from a given path (or a default location), parses the YAML, validates it, and returns the typed config object.
- A `parseConfig()` function that accepts a YAML string, parses it, validates it, and returns the typed config object. This is the primary entry point for tests.

### Validation rules

All validation follows the eager error collection pattern — gather every error, then throw them all at once in a `ConfigValidationError`.

**Top-level fields:**
- `domain` is required and must be a string
- `auth` is required and must be an object
- `auth.provider` is required and must be a string
- `auth.superusers` is required and must be a non-empty array
- `down_page`, if present, must be a string. File existence validation happens in `loadConfig()` (which has filesystem access), not in `parseConfig()` (which is a pure string parser used by tests). `parseConfig()` validates that the value is a string; `loadConfig()` additionally checks that the file exists on disk and reports an error if it does not
- `services` must be an object (map), defaulting to empty if omitted

**Service type inference:**
- A service with `dist` (and no `command`/`port`) is classified as a Pages service
- A service with `command` and `port` (and no `dist`) is classified as a local service
- A service with both `dist` and `command`/`port` produces a validation error (ambiguous type)
- A service with neither `dist` nor `command`/`port` produces a validation error (unrecognizable type)

**Service field validation:**
- Every service must have a `subdomain` field (string)
- `subdomain` must not be `admin` or `down` — these are reserved. The error message should name the service and the reserved subdomain
- Duplicate subdomains across services produce a validation error naming both conflicting services
- Duplicate ports across local services produce a validation error naming both conflicting services (port uniqueness only applies to local services since Pages services don't have ports)
- `database`, `bucket`, and `kv` are only valid on Pages services — if declared on a local service, produce a validation error naming the service and the invalid field
- `max_retries` is only valid on local services — if declared on a Pages service, produce a validation error
- `users` is only valid when `auth` is `authorized` — if `users` is present on a service with `admin_only` or `public` auth, produce a validation error
- Auth mode defaults to `admin_only` when not explicitly set
- The `functions` field defaults to `functions/` relative to the service's directory when not explicitly set on a Pages service

**Error messages:** Each error message should include the service name and the specific field or constraint that failed, following the personal-homepage pattern (e.g., `Service "photos" is missing required field "subdomain"`).

### Access selector utilities

Port the following utilities from the personal-homepage project, adapting them for the new auth model:

- `isWildcard()` — returns true if a string starts with `*@`
- `extractWildcardDomain()` — strips the `*@` prefix
- `mergeUsers()` — combines superusers with per-service users, deduplicating
- `toAccessSelectors()` — converts user strings to Cloudflare Access selector objects (email selectors for exact emails, email_domain selectors for wildcards)
- `buildServiceSelectors()` — adapted to work with the new auth model: returns empty array for `public` services, superusers-only for `admin_only` services, merged superusers + service users for `authorized` services

### Config differ

A function that compares two parsed config objects (old and new) and produces a structured diff. The diff describes:

- **Added services:** Services present in the new config but not the old
- **Removed services:** Services present in the old config but not the new
- **Modified services:** Services present in both but with changed fields. For each modified service, the diff should indicate which specific fields changed and categorize them:
  - Runtime-affecting changes: `auth`, `users`, `port`, `command`, `max_retries`
  - Pages-only changes: `dist`, `build`, `functions`, `database`, `bucket`, `kv`
  - Subdomain changes (both runtime and deploy-affecting)
- **Global auth changes:** Changes to the superusers list or identity provider

The diff structure should make it easy for the hot-reload engine (step 013) to determine which actions to take. For example, the engine needs to know "did this service's auth mode change?" and "did the global superusers list change?" without having to re-examine the raw config.

Comparing two identical configs should produce an empty diff (no additions, removals, or modifications).

### Tests

Follow the personal-homepage test patterns: `describe` blocks for parsing, validation, type inference, access selectors, and config diffing. Use the `expectValidationErrors()` helper pattern. Use YAML template literal constants for test fixtures.

**Parsing tests:**
- Valid Pages service config (has `dist`) parses and is classified as Pages
- Valid local service config (has `command` + `port`) parses and is classified as local
- Multi-service config with both Pages and local services parses correctly
- Optional fields (`build`, `functions`, `database`, `bucket`, `kv`, `max_retries`, `down_page`) are parsed when present
- Auth mode defaults to `admin_only` when omitted
- `functions` defaults to `functions/` when omitted on a Pages service
- Empty services section is valid
- Missing services section defaults to empty

**Validation tests (one test per rule listed above):**
- Missing domain, missing auth, missing provider, empty superusers
- Ambiguous type, unrecognizable type
- Reserved subdomains (`admin`, `down`)
- Duplicate subdomains, duplicate ports
- Cloud resources on local services
- `max_retries` on Pages services
- `users` on non-authorized services
- Non-existent `down_page` file
- Invalid YAML syntax
- Non-object YAML root
- Multiple errors collected and reported together

**Access selector tests:**
- Wildcard detection, domain extraction, user merging, deduplication
- Selector construction for exact emails and wildcards
- `buildServiceSelectors` for `admin_only`, `authorized`, and `public` services

**Config differ tests:**
- Identical configs produce empty diff
- Service added, service removed
- Service auth mode changed, port changed, command changed, users changed
- Global superusers changed
- Pages-only fields changed (marked as such)
- Multiple changes in one diff
