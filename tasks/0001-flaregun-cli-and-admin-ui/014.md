# 014: Admin UI frontend: project setup and service dashboard

## Context

This step initializes the admin UI frontend project and implements the first major view — the service dashboard. The admin UI is a React single-page application using Zustand for state management and Material UI (MUI) for the component library. It is served by the admin backend (step 012) at `admin.yourdomain.com` and communicates with the backend over same-origin HTTP (REST) and WebSocket connections.

The frontend is built at development/packaging time — the build output (index.html, JS bundles, CSS) is embedded within the CLI package so that `flaregun up` can serve it without any runtime build step. This means the project setup must include build tooling (bundler, TypeScript compilation) that produces static assets ready for the backend to serve.

The service dashboard is the default view when the admin UI loads. It shows all services from the config (both local and Pages) with their current status, and provides action buttons for managing local services. This step focuses on project scaffolding, build integration, state management, and the dashboard view. The config editor and log viewer are implemented in step 015.

There is no existing frontend code in the personal-homepage project — the admin UI is entirely new for flaregun.

## Related Code

Existing files/patterns to reference or extend:

- Step 012 (admin UI backend) — The backend provides the API the frontend consumes. The service list endpoint returns all services with lifecycle states for local services and deployment info for Pages services. The restart and stop endpoints accept a service name and delegate to the process supervisor. The frontend is served from the same origin as the API, so no CORS issues arise.

- Architecture directory layout — The frontend lives in `admin-ui/` at the project root, separate from the CLI source in `src/`. The build output is embedded into the CLI package (the exact embedding mechanism — file copying into a known path, or bundling into the package — is an implementation detail).

- Architecture component description — Material UI for the component library, Zustand for state management, React for the view layer. The frontend is a standard SPA with client-side routing.

## Reuse Opportunities

- **No existing frontend code** — This is a greenfield implementation. There is no frontend code in the personal-homepage project to reuse. However, the backend API contract from step 012 defines the exact shape of the data the frontend consumes.

- **Material UI component library** — MUI provides pre-built components for the dashboard layout (tables, cards, chips for status indicators, icon buttons for actions, app bars for navigation). This reduces the amount of custom component work.

- **Zustand for state management** — Zustand provides a lightweight store without boilerplate. The frontend needs stores for service state (polled from the backend), connection status, and later (step 015) config editor state and log streaming state.

## Deliverables

### Project initialization

Initialize a React + TypeScript project in the `admin-ui/` directory with the required dependencies and build tooling.

**Setup requirements:**

- React with TypeScript for the view layer
- Zustand for state management
- Material UI (MUI) for the component library, including the required MUI dependencies (core, icons, etc.)
- **Vite** as the bundler — it produces optimized static output (index.html, JS bundles, CSS) and integrates well with the Vitest test runner
- TypeScript configuration for the frontend (separate from the CLI's tsconfig, since the frontend targets the browser, not Bun)
- **Vitest** with **jsdom** as the test environment for React component testing, plus **React Testing Library** for component assertions. Configured in the Vite config with `test.environment: 'jsdom'`.
- A build script that produces the static assets in a predictable output directory (e.g., `admin-ui/dist/`)

### Build output embedding

Ensure the frontend build output is embedded into the CLI package so the admin backend can serve it.

**Behavior:**

- The frontend build produces static assets (index.html, JS bundles, CSS files) in `admin-ui/dist/`
- The CLI references these assets at the path `admin-ui/dist/` relative to the project root. The admin backend (step 012) accepts the SPA directory path as a parameter — at runtime the orchestrator passes the resolved path to `admin-ui/dist/`
- The admin backend (step 012) serves these files as static assets — the embedding mechanism must produce files at a path the backend can discover
- A build script at the project root should build both the CLI and the frontend (or at minimum, a documented command to build the frontend before packaging the CLI)
- The frontend does not need to be rebuilt at runtime — the pre-built assets are shipped with the CLI

### Application shell and routing

The top-level React application with navigation between views.

**Behavior:**

- The application shell provides a layout with a navigation mechanism for switching between views: the service dashboard (this step), and the config editor and log viewer (step 015)
- Use client-side routing — the backend returns `index.html` for all unmatched routes (SPA fallback configured in step 012), so deep links to specific views work
- The navigation should be clear and accessible — a sidebar, top tabs, or another standard navigation pattern
- The application shell includes a header or toolbar area showing the domain name (fetched from the config read endpoint) and the tunnel connection status indicator

### Zustand store: services

A Zustand store that manages service state fetched from the backend.

**Behavior:**

- Fetch the service list from the backend's service list endpoint on initial load
- Store the full list of services with their current states (lifecycle state, uptime, restart count for local services; type and deploy info for Pages services)
- Provide actions for triggering restart and stop — these call the backend's REST endpoints and update the store with the response
- Poll the service list endpoint at a regular interval (e.g., every few seconds) to keep the dashboard up to date with state changes (services crashing, restarting, state transitions)
- The polling interval should be short enough that state changes appear responsive but not so aggressive that it overloads the backend
- Provide a method to force an immediate refresh (used after triggering a restart/stop to show the result faster than the next poll cycle)

### Service dashboard view

The main view showing all services and their current status.

**Behavior:**

- Display all services from the config in a list or card layout
- For each service, show:
  - **Service name** — the config key name
  - **Subdomain** — the full subdomain URL (e.g., `music.yourdomain.com`)
  - **Service type** — visual indicator distinguishing local services from Pages services
  - **Status** — current lifecycle state for local services:
    - `running` — shown with a positive/green indicator
    - `crashed` — shown with an error/red indicator
    - `restarting` — shown with a transitional/yellow indicator
    - `stopped` — shown with a neutral/gray indicator
    - `starting` — shown with a transitional indicator
  - **Uptime** — for running local services, display how long the service has been running (formatted as a human-readable duration)
  - **Restart count** — for local services, show how many times the service has been restarted
  - **Last crash reason** — for crashed or recently-crashed services, show the exit code or error message
- For Pages services, show the service type and subdomain. Status for Pages services is simpler — they are either deployed or not deployed (from lock file info). No uptime or restart count applies.
- **Action buttons** for local services:
  - **Restart** — triggers a restart via the backend's restart endpoint. The button should show a loading/pending state while the restart is in progress. After the backend responds, refresh the service state.
  - **Stop** — triggers a stop via the backend's stop endpoint. Same loading/pending pattern. After the response, the service should show as `stopped`.
  - Action buttons are disabled or hidden for Pages services (they are not managed by the process supervisor)
  - Action buttons are disabled for services already in the `stopped` state (stop is a no-op) or in `restarting` state (wait for the current restart to complete)

### Tunnel connection status indicator

A persistent UI element (in the application shell, not specific to the dashboard) showing whether the cloudflared tunnel is connected.

**Behavior:**

- Display a visual indicator (icon, badge, or chip) showing the tunnel connection state: connected or disconnected
- The tunnel status is fetched from the backend (either as part of the service list response or a dedicated endpoint — the backend can report tunnel status alongside service states)
- Connected state shows a positive indicator (green dot, "Connected" text, etc.)
- Disconnected state shows a warning indicator (red dot, "Disconnected" text, etc.)
- The indicator updates on the same polling cycle as the service list

### Tests

Frontend tests use **Vitest with jsdom** as the test environment and **React Testing Library** for component testing. Bun's test runner does not natively support DOM environments, so the frontend uses Vitest (which integrates well with Vite-based projects and provides jsdom/happy-dom support out of the box). Add vitest, @testing-library/react, @testing-library/jest-dom, and jsdom as dev dependencies. Configure vitest with `environment: 'jsdom'` in the frontend's vite config. Backend API calls are mocked using `vi.fn()` or `msw` (Mock Service Worker).

**Service dashboard tests:**
- The dashboard renders all services returned by the service list endpoint
- A local service in `running` state displays with a positive status indicator and uptime
- A local service in `crashed` state displays with an error indicator and restart count
- A local service in `stopped` state displays with a neutral indicator
- A Pages service displays with its type indicator and subdomain
- Pages services do not show restart/stop action buttons
- Clicking the restart button for a local service calls the restart endpoint
- Clicking the stop button for a local service calls the stop endpoint
- Action buttons show a loading state while the API call is in progress
- After a successful restart/stop, the service state is refreshed

**Tunnel status tests:**
- When the tunnel is connected, the indicator shows a connected state
- When the tunnel is disconnected, the indicator shows a disconnected state

**Store tests:**
- The service store fetches the service list on initialization
- The service store updates when polling returns new data
- Calling the restart action sends a request to the restart endpoint and refreshes
- Calling the stop action sends a request to the stop endpoint and refreshes

**Build and embedding tests:**
- The frontend build produces index.html, at least one JS bundle, and CSS output
- The build output is placed in the expected directory for the backend to serve
